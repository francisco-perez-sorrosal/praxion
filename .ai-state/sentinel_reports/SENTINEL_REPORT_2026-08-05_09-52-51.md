## Note on the deliberately-unfixed finding (I1)

The prompt asked for an independent read on whether filing the staleness finding as tracked debt with evidence is the right disposition, rather than refreshing the markers. **It is, and the reasoning generalises past this instance.**

A `<!-- last-verified: D -->` marker is not a freshness timestamp — it is an **assertion that a human or agent checked this content against reality on date D**. Refreshing it without re-verifying does not make the content fresher; it converts *"nobody has looked recently"* into *"someone looked and confirmed"*. That is strictly worse than the stale state, because a stale marker is honest about its own ignorance while a falsely-refreshed one destroys the only signal that would ever catch the error.

This is not hypothetical here — it already happened once, and I re-derived the evidence independently rather than taking the ledger row's word for it. The `communicating-agents` markers are dated 2026-05-01 (96 days before today, by my own measurement). A2A v1.0.0 shipped 2026-03-12. Those sections were **already wrong seven weeks before** they were last certified. A marker sweep is exactly the operation that produced the current state.

So the correct disposition of an F08 WARN is never "bump the date". It is "re-verify, then either re-mark or correct". When re-verification finds the content wrong — as it did for 22 of ~35 sections — the remaining work is content correction across six skills, which is a scoped pipeline, not a sentinel-run action. A ledger row with per-section evidence and URLs is precisely the mechanism the ecosystem provides for *known defect, scoped work required, cannot be done now*. `td-114` carries that evidence and names the artifacts. Right call.

**Three caveats I register rather than leave implicit:**

1. **A ledger row is a commitment, not a suppression.** F08 must keep reporting all 27 WARNs on every run until the content is corrected. This report does. If a future run cites `td-114` to *omit* the finding, the row will have become a silencer.

2. **What is known got materially worse even though the check result did not move.** Last run's I7 was "27 markers are stale" — an age proxy. This run it is "~22 verified sections are factually wrong" — a correctness defect in shipped skill content that agents load and act on. The WARN count is identical; the severity of the underlying reality is not. Anyone reading the count alone will under-read this.

3. **The marker protocol cannot express what we now know.** A marker records *when* something was checked, with no vocabulary for *what the check found*. There is no way to write "verified 2026-08-05: WRONG, correction pending `td-114`" — so the next sentinel run sees an old date and infers only neglect, and the next agent to load `communicating-agents` gets no warning at all that its content is known-false. That gap is worth a `verified-incorrect` marker state in `rules/swe/staleness-policy.md`, and it is the most durable thing this episode surfaced.
