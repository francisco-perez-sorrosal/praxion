## Feature Summary

Gives every spawned Praxion agent its role's slice of the Praxion process as a generated per-role kernel, so that a pilot role can stop inheriting the instruction files only on measured evidence.

Before this change a spawned agent got its process by inheriting the orchestrator's whole rulebook (about 18.3K tokens per spawn for the researcher and the verifier), plus three universal blocks that every definition carried by hand. The startup-context diet could not switch that inheritance off, because a lean spawn then lost its process: a lean verifier without a kernel went looking for the user's instruction file in 3 of 3 smoke sessions of the adherence eval. This change adds the channel that makes a lean spawn safe, and the gate that keeps a role from going lean on an estimate.

The mechanism has six parts. `rules/_audience.yaml` is a hand-authored manifest that gives every section, or part of a mixed section, of every always-loaded source exactly one scope (core, role, orchestrator-only, no-actor) and one form (verbatim, or condensed with a pinned digest); the always-loaded set is found from the repository, never listed. `scripts/generate_kernels.py` writes one committed kernel file per module under `claude/kernels/`, a JSON index, the three universal blocks inside every agent definition (they stay there as the never-to-nothing fallback, now with one source) and the host-native preamble. `scripts/check_kernel_manifest.py` is the commit gate: ten invariants (totality, a core for every agent, the contract byte-identical, the 10,000-character cap, group coherence, fresh pins, no orchestrator text in a kernel, no stale kernel, the ledger's rules, the hook reading every ledger record as PyYAML does), each with a canary, plus a `--liveness` mode that names a spawn of a delivering role that left no `kernel_injected` row. `hooks/inject_kernel.py` runs as synchronous `SubagentStart` slot entries and injects the role's kernel, and the working project's root `CLAUDE.md` whole and verbatim, for roles the adoption ledger records at trial or switched, leaving one `kernel_injected` row per delivering spawn. `.ai-state/kernel_adoption.yaml` records each role's moves: absent, trial, then switched on a passing run with the user's ratification, or held (a trial closed without a flip, with its reason and every run); a held role may be re-opened as a new trial. The Codex exporter embeds the same strings and drops `omitClaudeMd`; the Cursor export is byte-identical; the adherence eval refuses to score a lean session whose kernel did not arrive, and its task kits carry a convention written only in the fixture's `CLAUDE.md`, so a lost project file shows as a measured regression.

The pilot closed with one role switched and four held. The researcher passed the flip rule on a 24-pair run (`20261014T152926Z-723e7a`: no regression on any scored mechanical check, the judged assumption-and-objection check non-inferior at 18 of 18 in both arms, observed judge error on the golden cases 0.50 stated as dec-459 asks), the user ratified the flip, and the researcher's first request fell from 47,631 to 27,016 tokens on the startup probe (FC-04, strict MCP profile). The verifier ran 24 pairs and did not pass: the forced-stop partial-title check read 6 of 9 in the full arm against 0 of 9 in the lean arm, and two single-pair differences count under the zero allowance; a diagnostic draw found no kernel text missing. The context-engineer's smoke kit yielded 3 pairs, equal on every scored check, and the discipline-consultant and skill-genesis kits are smoke kits too, so no run of the three could reach the 20-pair floor. The user chose to close the pilot rather than build full kits. Closing four roles at trial would have injected a kernel and the project file at every spawn of those roles in every managed project, so a third adoption status, `held`, was added at close (architect amendment of 2026-10-15): those four roles fall back to today's behaviour, keep their record and every run, and receive nothing at spawn. Every claim in this spec is bounded non-regression within the declared margin, never improvement, and every saving is a startup-probe reading.

Requirements REQ-10 and REQ-17 (with AC-10, AC-17 and the limit note of FC-05) carry the 2026-10-15 amendments for the held status and, in REQ-17, the bound on a re-opened trial's start answered as the final verifier's spec question SQ-06 (a start after the commit it follows and no later than its own re-opening). The requirement text below is the amended text, verbatim.

### REQ-01: Every always-loaded section has exactly one audience

**When** a maintainer commits a change to any always-loaded source (a rule file with no path scope, `claude/config/CLAUDE.md.tmpl`, the project `CLAUDE.md`) or to `rules/_audience.yaml`
**the system** refuses the commit unless every section heading from level two to level four of every such source, and every part of a section split by audience, has exactly one entry in `rules/_audience.yaml` and every entry names a heading or part that exists, naming each unclassified section or part and each orphaned entry; the set of always-loaded sources is found from the repository, never kept as a hand-written list, so a new rule file with no path scope is covered without editing anything else; a managed project's own `CLAUDE.md` is never classified, and a file that is not always loaded but contributes text to a kernel registers only the sections it contributes
**so that** no guidance can enter, be renamed in or leave the resident layer without someone deciding which audience it serves.

### REQ-02: An audience entry is one of the legal shapes

**When** an entry of `rules/_audience.yaml` is read
**the system** accepts it for a whole section, or for a part of a mixed-audience section named by the heading plus a leading-text prefix unique within that section, and only with exactly one of four scopes (core; role, naming at least one existing agent or declared group; orchestrator-only, with a non-empty reason; no-actor, with a non-empty reason) and, for core and role, exactly one of two forms (verbatim; or condensed, carrying the pinned digest of the source section it condenses), and refuses with a message naming the entry: an empty audience, an unknown agent or group, an empty group, a condensed form without a pin, a pin that no longer matches its source section, two entries for one section, and an orchestrator-only or no-actor entry that names an agent
**so that** every section's audience is a legal state and nothing downstream has to guess what an ambiguous entry meant.

### REQ-03: Classifying deletes nothing and leaves the main session whole

**When** the manifest, generator, kernels and checker land
**and** a section is classified orchestrator-only or no-actor
**the system** deletes or rewords no section of any rule, of `claude/config/CLAUDE.md.tmpl` or of the project `CLAUDE.md`, and the main session still receives every always-loaded section it received before
**so that** guidance moves to its audience instead of being cut: a trim is a move into an artifact, never a deletion.

### REQ-04: Kernels are generated, committed and never stale

**When** a maintainer runs `scripts/generate_kernels.py`
**the system** writes one committed file per module under `claude/kernels/` (the core and each role module; a module above the size cap as numbered parts) and regenerates every artifact derived from the same sources (the three universal blocks in every agent definition and the preamble's contract wording), all byte-identical on every run from the same sources, and its check mode reports, without writing, any committed kernel that differs from what the current sources produce; the commit gate refuses a stale kernel
**so that** the text every spawn receives is reviewable in a diff and cannot drift from the rules it is derived from.

### REQ-05: The core carries the process every role shares

**When** any role's kernel is assembled
**the system** includes the core, which carries: the behavioral contract's four behaviors and its self-test, byte-identical to the contract rule's own text; a pointer to where the Praxion principles can be read from a spawn; where things live (the task slug scoping all work under `.ai-work/`, permanent state under `.ai-state/` written only where the role says, scoped fragment files when agents run concurrently, never committing, never a bare stash or discard in a shared tree); the return contract (a pointer of at most about fifteen lines ending in exactly one of `[COMPLETE]`, `[BLOCKED]`, `[CONFLICT]` or `[PARTIAL]`); the partial-output form (a `[PARTIAL]` title with Completed phases, Stopped at and Usable sections lines); staying within the role and naming the agent that owns out-of-role work; checking current official documentation before relying on an external interface; the rule for resolving Praxion links from any project; and the sentence "The user-level instruction file is not loaded for you and must not be sought as instructions; your kernel carries what you need from it."; and no kernel names a specific decision record number, requirement id or dated state file
**so that** a spawn that inherits nothing still knows its own part of the Praxion process and does not go hunting for the user's file, as a lean verifier did in 3 of 3 smoke sessions.

### REQ-06: Principles cited by a role are reachable from any spawn

**When** a spawned role follows the principles pointer, or a principle its own definition cites by name (the verifier anchors coupling findings to the Balanced Coupling principle)
**the system** gives the verifier the Balanced Coupling and Incremental Evolution principles verbatim in its own kernel, and leads any other principle reference to readable text of that principle without reading `~/.claude/CLAUDE.md` and without reading any file outside the running plugin and the project
**so that** a role told to align with or cite a principle can still do so under `omitClaudeMd`, and no role is sent to the user-level file to do its work.

### REQ-07: Each role receives the core and exactly its own modules

**When** the kernel for a role is assembled
**the system** adds to the core the role's modules and nothing else: the ADR-author module for systems-architect, implementation-planner, interface-designer and agentic-transactions-architect; the ledger-writer module for verifier, sentinel and architect-validator; the principles digest for promethean and systems-architect only; the principles-anchor module (Balanced Coupling and Incremental Evolution, verbatim) for verifier; the delegator module for roadmap-cartographer; the ADR-reader module (the discovery protocol) for researcher and verifier; the ledger-consumer module for the roles whose definitions cite it; and any further text the manifest scopes to that role; a role's modules follow from the sections its definition cites, so every section of a registered source that a definition cites reaches that role through its kernel or a named other path; the verifier receives no ADR-author module; no text the manifest classifies orchestrator-only or no-actor appears in any kernel
**so that** each spawn carries its own part of the process and none of the orchestrator's playbook.

### REQ-08: Every agent gets a kernel without a roster, and groups match behaviour

**When** an agent definition is added to or removed from the agents directory
**the system** produces or drops its kernel (at least the core) without anyone editing a list of agents, and refuses a commit in which the ADR-author group differs from the set of agents whose definitions write ADR draft fragments, or the ledger-writer group differs from the set whose definitions append tech-debt ledger rows, in either direction
**so that** a new agent is aligned by default and group membership cannot silently disagree with what agents actually do.

### REQ-09: Every injected string fits the harness cap

**When** any kernel text is injected
**the system** keeps each injected string at or under 10,000 characters, delivers a module above the cap as numbered parts in order whose concatenation equals the module, always puts the behavioral contract in the first string a role receives, and refuses a commit that would produce a larger string; the core's token size is reported and never decides a commit
**so that** the harness never replaces kernel text with a file path and a preview the model is not told to read, and the gate stays deterministic and offline.

### REQ-10: A spawned Praxion agent receives its kernel before its first turn

**When** a Praxion agent is spawned in any project (the Praxion checkout, a managed project, or an unmanaged directory)
