## Key Decisions

- **The liveness checks move to a workflow of their own, one job per kind of check, none waiting for another** (the decision draft on the liveness workflow; it partly supersedes `dec-419`).
  - Evidence: `dec-419`'s reversal trigger fired (the canaries job cancelled at 45.7, 45.3 and 45.3 minutes), and the red liveness jobs had held `Test (scheduled)`'s diff base back for seven weeks.
  - Rejected: larger limits in the same file (the red jobs would keep deciding the scheduled run's conclusion) and `dec-419`'s own two-job layout in a new file (a slow audit would still cost the fast probes their verdicts, and a slow whole-suite scenario would still cost the quick ones theirs). The decision takes `dec-419`'s steelmanned runner-up.
  - Cost: five runner setups of 10 to 40 s each, against five independent verdicts; one more invariant test. Accepted: the audit job and two whole-suite scenarios are red every week until td-500 is answered, visibly and outside autofix.
  - **Reversal trigger:** any job that uses more than 80 percent of its limit in a weekly run is re-sized from that run's own durations.
- **The audit's bound is one key in `pyproject.toml`, read from one place, with no fallback.** It is data, not code: a scratch copy can declare a short bound by editing one line, and the probe, the command's time limit and the whole-suite scenarios cannot drift apart. A constant in the probe would make a driver patch source code; a value in the workflow would leave a local run with no bound and split the source between YAML and Python; an environment override is scrubbed by the command and would re-couple the audit to the step loop's reader. An undeclared bound fails the audit naming the key, instead of silently borrowing the step loop's 1500 s.
- **A cut scenario reports through a file and an `if: always()` step.** GitHub signals only the step's entry process (bash), then kills the tree, so a pytest summary or a signal handler inside pytest never runs under a time limit. Each scenario step carries a step limit two minutes under its job's, so the report step has time to run. Rejected: `--durations`, junit output, signal handlers and a per-node shell loop (which breaks the acceptance driver's literal pytest-line contract). An accepted cost: a cut scenario's figure is an upper bound by the kill's grace (at most 10 s).
- **Each limit is sized by one stated rule and a machine-checked line.** Limit = `max(10, ceil((1.5 x (step x scale + setup) + fixed) / 60))` minutes, at most 240 (two-thirds of the runner's 6-hour maximum, so a job at 80 percent of its limit still has room before it must split). `scale` is 1.53, the ratio of the runner's untraced root suite to the local one; `setup` is 10 s; `fixed` is 360 s for the audit (the command's own allowance) and 180 s for the whole-suite jobs (their runner-freeing step, unmeasured). The 10-minute floor was added on 2026-11-18, after the design sized the fast job near two minutes: runner setup varies by minutes. The audit's bound is `ceil(1.5 x 1527 x 1.53 / 60) x 60 = 3540` s, and the job's 69 minutes holds it with its 360 s and the setup. The scale was taken from the parallel untraced suite and applied to serial scenarios and to the traced audit; the verifier called this a load-bearing assumption (L7) that the first runner run checks.
- **The whole-suite jobs are grouped by whether a scenario needs the audit to pass** (a rework after verification, replacing a collection-order split). The first split put one red-by-design scenario in each job, so both were red every week and neither could show a new failure (the verifier's L6). Now `scenarios-whole-suite` (201 minutes) holds the four that do not need the audit to pass and `scenarios-whole-suite-audit-gated` (135) the two that wait for td-500; each job deselects the other's nodes by id, and a later scenario runs in both until placed.
- **The measurement is a step of its own, taken on the last code commit, in the user's window, with nothing else running.** Cheapest first (fast probes, the untraced root pocket, the audit's command, the quick scenarios, the whole-suite scenarios), a disk sampler beside them, every reading recorded with its commit. Local peak disk use was 28.3 GiB, an upper bound (`df` on macOS reads the APFS container); above the 10 GB the spec's SQ-06 named, so each whole-suite job frees the runner's unused toolchains first. The retention-policy option was not taken: it governs only the outer pytest session, while nested sessions keep their own roots and the two scenarios that fail weekly keep their copies.
- **Paired runs keep their own results directory** (the decision draft on the paired runs' results directory; precedent `dec-477`, which gave the moves' results their own subdirectory outside the flip gate's read surface). The axis record gains `results_subdir`; the default axis keeps `.ai-state/eval_ledger/adherence`, the paired axis gets `.../refactoring-delivery`, and `--close` and `--continue` search every axis's directory (a run held in two is read from the named axis first). Rejected: teaching the adoption gate's reader and its parity test to skip another axis's files by name, which couples the flip gate to eval axes.
- **The other two rows, decided in the ledger notes rather than a decision record** (neither changes a component boundary). td-672 is prevention only: the count comes from the paid loop's own `session_slots`, and a spend-refused paired run is still closed and run again, because letting it continue would reverse a refusal the paired axis' spec declared. td-673 is half fixed: the refusal is named from the stream, which already holds it; pre-approving the `Agent` tool would change how the instrument's sessions start, its readings are compared across dates (`dec-457`), and proving no change needs paired paid readings, so that half is re-filed on td-673 with the run card as its condition.

The lesson step's files are disjoint from every code step's, and none is always loaded (`rules/swe/testing-conventions.md` is path-scoped), so FC-01 did not move.
