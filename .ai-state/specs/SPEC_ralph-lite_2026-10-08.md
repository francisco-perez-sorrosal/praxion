## Feature Summary

A well-gated single-behaviour task can be handed to a bounded, unattended loop -- the step-loop driver's goal mode, Ralph-lite -- in which every iteration is a fresh headless process, ground truth decides each iteration, the worker never commits, protected paths are denied and caught, every iteration leaves a ledger record with turns and cost, and every stop leaves a handoff; entered through the `/praxion:ralph-lite` skill, never a command, on Praxion and on every managed project.

## Requirements

The requirements describe Ralph-lite at its surface: the driver's command and its two new verbs, the files a goal scaffold leaves, the process each iteration starts, the documents the loop reads and writes, the skill's invocation and the texts a reader follows. These terms recur:

- *the driver* is the step-loop driver's command declared below;
- *a goal step* is a plan step that carries an `Iterations:` field, and *a goal plan* is a plan whose one step is a goal step; *an ordinary step* carries no `Iterations:` field;
- *an iteration* is one spawn request for a goal step together with the return recorded against it; an iteration is *progressing* when the driver commits it, that commit being its *unit*, and *non-progressing* otherwise;
- *the worker* is the `claude` process the `run` verb starts for an iteration;

- *the attempt cap* is the existing cap of two fresh attempts for an ordinary step;
- *a stop for a human* is a `needs-human` outcome with exit 2 that names the step and its cause and leaves `HANDOFF.md`.

Requirement ids are this pipeline's own and appear nowhere in code, tests or docstrings. Two requirements carry the intent of two requirements of the archived specification of the pipeline that built the driver, with their text amended; the Spec Notes record the mapping.

### REQ-01: The goal verb scaffolds a one-step goal plan

**When** a user runs `step_loop.py goal <slug> --goal <sentence> --check <command> --expects <expectations> --paths <path>... --protect <path>... --iterations <n>` for a task whose working directory holds no `IMPLEMENTATION_PLAN.md`
**the system** writes in `.ai-work/<slug>/` an `IMPLEMENTATION_PLAN.md` holding exactly one step, assigned to the implementer, whose `Files:` are the paths given to `--paths`, whose `Read-only:` names the paths given to `--protect` with those under `tests/acceptance/` or `tests/e2e/` first, whose `Check:` is the given command and expectation in the existing check grammar, whose `Iterations:` is the given number, whose `Done when:` is the check met with no protected path changed, and whose body states the goal sentence; a `WIP.md` holding that step unticked and an empty `## Progress record` section; and a `TASK_BRIEF.md` whose one Key Signal is the goal and whose Health Guards name the protected paths; it prints one JSON object on standard output naming the slug and every file it wrote, and exits 0; the reconciler and `status` then read the plan as one step, not yet complete, with no error
**so that** everything an iteration needs lives in the task's files and in git, in the documents every existing reader already parses

### REQ-02: The scaffold denies the protected paths at the harness

**When** `goal` scaffolds a goal plan in a repository
**the system** adds to `.claude/settings.local.json` at that repository's root, under `permissions.deny`, one deny rule per protected path in the form the harness consults for every file-writing tool (an edit rule naming the path's pattern; a write rule, which the harness accepts but never consults, is not required); it creates the file when absent, keeps every entry the file already held, and adds no rule twice
**so that** the worker cannot change a protected path even when it tries, in any permission mode

### REQ-03: The goal verb refuses what it cannot scaffold safely

**When** `goal` is given a task whose working directory already holds an `IMPLEMENTATION_PLAN.md`; a command or an expectation the existing check grammar does not accept; an `--iterations` value that is not a whole number of at least 1; no `--paths`; or a `--paths` entry under a protected path
**the system** writes nothing, prints an `error` envelope whose message names what it refused, and exits 4
**so that** a goal plan never overwrites a plan and never scaffolds a loop that could not be gated or could never succeed

### REQ-04: The run verb drives a goal plan to an outcome

**When** a user runs `step_loop.py run <slug>` on a task whose plan holds a goal step
**the system** repeats three moves, taking the next action as `next` gives it, starting the worker for a `spawn` and waiting for it to exit, and recording the worker's return as `record` does, until the outcome is not a `spawn`; it then prints that outcome's envelope on standard output, the same envelope `next` or `record` prints for it, and exits with its code: 0 for `complete`, 2 for a stop for a human (`stalled` among its causes), 3 for `budget-exhausted`, 4 for a caller error and 1 for `internal`; a task whose next action is already not a `spawn` starts no worker; a plan holding no goal step is refused with exit 4 before any worker starts
**so that** one command takes a goal to its end or to a named stop, through the same verbs and the same gate as every other driven step

### REQ-05: Each iteration prints one line with its cost

**When** `run` has recorded an iteration
**the system** writes one line to standard error, beginning `step_loop: `, naming the request id, whether the iteration committed a unit and the commit when it did, the worker's turns, the worker's cost in US dollars as the decimal text its result object reported (a currency sign may surround it), and the number of permission denials whenever the result object reported any
**so that** a person watching the loop sees what each iteration did and what it cost, as it happens

### REQ-06: The run verb keeps the base it was given

**When** `run` is started with `--base-ref <ref>`, `--repo-root <dir>` or `--worktree-root <dir>`
**the system** takes every gate reading, verdict and stop handoff of the loop against that base and those roots, and every command it prints for a person to run next, a stop's `resume` included, carries the same options with the same values; started without them, it takes the defaults `next` takes
**so that** a loop whose base differs from the merge-base default keeps that base on every call, with nothing appended by hand

### REQ-07: Each iteration is a fresh worker with a fixed safety profile

**When** `run` starts the worker for a spawn request
**the system** starts one new process, the first `claude` on `PATH`, in the repository root, in print mode with the request's three-line prompt verbatim, and with `--model` naming the request's model, `--max-turns` with a per-iteration turn bound, `--max-budget-usd` with a per-iteration dollar fuse, `--permission-mode dontAsk`, `--permission-prompts none`, an `--allowedTools` list that names the goal's check command and the test-scope resolver and no other shell command, and `--output-format json`; it never continues or resumes an earlier session, never passes `bypassPermissions` or `--dangerously-skip-permissions`, and never passes `--bare` in this increment (an explicit opt-in surface for it is a later increment's, because it drops the project's standing instructions, rules and hooks)
**so that** each iteration starts from a fresh context, bounded in turns and in dollars, and can run the goal's check unattended without being able to run anything else

### REQ-08: The worker's result is read, never guessed

**When** the worker exits
**the system** reads the JSON result object on its standard output and relays to `record` the result's `session_id` as the agent id, and the terminal marker on the last line of the result's `result` text, or `none` when that line carries none or the object carries no `result` text; a worker the harness stopped at its turn bound, whose `subtype` is `error_max_turns`, is recorded with stop reason `turn-cap`; a worker that could not be started, because no `claude` is on `PATH`, or that exited with no result object, is relayed to `record` as not started, and `run` stops with exit 4 and a message naming the cause
**so that** what the ledger says about an iteration comes from what the harness reported, and a failure to start is never mistaken for an attempt

### REQ-09: The worker's transcript is found where the harness writes it

**When** `record` is given as the agent id the session id of a top-level session, as the worker's is
**the system** finds that session's transcript at `<config>/projects/<project>/<session id>.jsonl`, where `<config>` is `CLAUDE_CONFIG_DIR` when set and `~/.claude` otherwise, and `<project>` is the session's working directory with every character that is not a letter or a digit replaced by a hyphen, and reads from it, as from a subagent's transcript, the first user text, which must name the request, the end, the marker and the count of distinct requests; a subagent's transcript is found and read exactly as before, by the driver and by the turn-budget reminder alike
**so that** the gate judges a headless worker on the same evidence it judges a subagent on

### REQ-10: An exited worker is an ended worker

**When** `run` records an iteration whose worker process has exited
**the system** treats the worker as ended and never answers `agent-running` for it, even when the transcript's last request ends on a tool call, as it does when the turn bound stopped the worker
**so that** the loop never waits on, or refuses, a worker that is already gone

### REQ-11: The ledger records each iteration's turns and cost

**When** an iteration whose worker `run` started is recorded
**the system** appends one record to `ITERATION_LEDGER.jsonl` carrying the request id as `request`, the session id as `agent_id`, the worker's turns counted from its transcript as every reader counts an agent's distinct requests, the per-iteration turn bound as `max_turns`, and the result object's `total_cost_usd` as `cost_usd`; every record without `cost_usd`, as the relay and a person write them, reads, counts and composes a handoff exactly as before; `python3 scripts/iteration_ledger.py read <slug> --json` shows `cost_usd` on each record that has it
**so that** turns and cost are read per iteration from the one ledger every reader shares

### REQ-12: Each iteration's prompt carries the goal's state from disk

**When** `next` issues a spawn request for a goal step
**the system** writes `PROMPT_<id>.md` holding the goal sentence; the check command and its expectation; the check's latest reading, or a statement that there is none yet; the lines of `## Progress record` so far; the paths in scope and the protected paths; the patch files left by earlier non-progressing iterations; the request id; and the finish ordering: pick one unit of the goal, finish it, leave the tree committable, append one line to `## Progress record` saying what was done, what remains and what was learned, run the check and show its last lines, never commit, and end with a terminal marker, `[BLOCKED]` when the goal cannot be met as stated
**so that** a fresh context starts every iteration from the files alone, knowing what was done and what remains

### REQ-13: The gate holds the goal's own failing tests as pending

**When** `record` gates an iteration of a goal step
**the system** runs, as for any step, the derived test scope of the paths the iteration changed and then the goal's check, and reads a failing test as `pending` exactly when it is one of the goal's targets, and every other failing test as a failure that makes the iteration red
**so that** the tests the goal exists to turn green never block a step toward it, while a break anywhere else still does

### REQ-14: Only a progressing iteration is committed

**When** an iteration of a goal step has been gated
**the system** commits it by pathspec, with the `Step-Loop-Request:` trailer naming its request, exactly when the gate is not red; the check's counts have not regressed against the reading at the last committed iteration, failures not higher and passes not lower, or, before any commit, against the reading taken before the first iteration; the iteration changed at least one path in `Files:`; and `## Progress record` gained a line; otherwise it commits nothing, keeps the iteration's diff as a patch file in the task's working directory named by its request id, and records the iteration as non-progressing; a protected path or an outer-loop test is never in a commit
**so that** every unit the loop keeps is green, no worse than the one before, real and explained, and the work of a failed iteration stays recoverable without entering history

### REQ-15: A changed protected path stops the loop

**When** an iteration leaves a change under a protected path
**the system** commits nothing from that iteration and makes it a stop for a human whose `evidence` names the changed path
**so that** a worker that got past the deny rules is caught at the gate, and no protected change reaches a commit

### REQ-16: The goal's check decides completion

**When** an iteration of a goal step meets the goal's check, with the gate not red and no protected path changed
**the system** commits it as it commits any progressing iteration and ticks the step in `WIP.md`, and the next `next`, and `run`, end with `complete` and exit 0; a `[COMPLETE]` return whose check is unmet never completes the step
**so that** the goal is done when ground truth says so, never when the worker says so

### REQ-17: The iteration field is the goal's budget

**When** `next` or `run` reads a goal plan
**the system** reports in the envelope's `iterations` a budget equal to the goal step's `Iterations:` value; once that many iterations are recorded and the goal is not complete, the next action is `budget-exhausted` with cause `iteration-budget` and exit 3; no spawn request's `attempt` for a goal step exceeds its `Iterations:` value; a plan with no `Iterations:` field gets exactly the budget it gets today
**so that** a goal loop is bounded by a number its plan states, and ordinary plans keep the budget they have

### REQ-18: Two non-progressing iterations in a row stop for a human

**When** the latest two recorded iterations of a goal step both committed nothing
**the system** makes the next action a stop for a human with cause `stalled`, naming the step, whose `attempts` list those two iterations, before any further iteration; a progressing iteration resets the count, so iterations that alternate between progressing and not never stall; a stall is reported ahead of a spent budget; a `[BLOCKED]` or `[CONFLICT]` return is a stop for a human at once, as for any step
**so that** a goal that stops converging reaches a person after two wasted iterations, never after the whole budget

### REQ-19: An ordinary step keeps its two attempts

**When** an ordinary step's attempts end unverified
**the system** makes it a stop for a human with cause `attempts-exhausted` after exactly the attempt cap of two, with the same `Attempts:` replan line, the same envelope and the same handoff as at the pipeline base, and the reconciler reads it `attempts-exhausted` as it does today
**so that** goal mode changes nothing about how an ordinary step is bounded

### REQ-20: Every reader agrees whether a step is spent

**When** a goal step is read by `next`, `record`, `status` or `python3 scripts/reconcile_pipeline_state.py <slug> --json`, at any count of recorded iterations
**the system** gives one answer: the reconciler reads the goal step `attempts-exhausted` exactly when the driver's next action for it is the `stalled` stop, and otherwise reads it by its check and its outstanding iteration as it reads any step, complete, in flight or not yet complete, whatever the count; `status` names, in its table output and in the next-action field of its JSON object, the next action `next` would take, the cause of a stop included
**so that** the ground-truth reader never sends a progressing goal to a person at its second iteration, and the loop and the reconciler never disagree

### REQ-21: A goal plan runs through the relay as through the runner

**When** a goal plan is driven through the relay, `next`, the Agent tool, then `record` with the agent id and the marker, as `/praxion:step-loop <task-slug>` drives it, instead of through `run`
**the system** applies to each iteration the same prompt, gate, commit rule, budget and stall stop as under `run`, and its records carry no `cost_usd`
**so that** the in-session form and the terminal form are one loop with two ways of starting a worker

### REQ-22: Ordinary plans are untouched

**When** a plan, a `WIP.md` or an `ITERATION_LEDGER.jsonl` written without an `Iterations:` field, a `## Progress record` section or a `cost_usd` key is read by `next`, `record`, `status`, the reconciler, `python3 scripts/spawn_count.py`, `python3 scripts/iteration_ledger.py` or `python3 scripts/compose_handoff.py`
**the system** produces exactly the result each produced at the pipeline base, and `next`, `record` and `status` keep their arguments, envelopes and exit codes
**so that** goal mode is additive, and every pipeline that runs today runs the same way afterwards

### REQ-23: The skill is the entry, never a command

**the system** runs the skill `skills/ralph-lite/SKILL.md`, which the user and the model can both invoke and whose body receives the typed arguments; its description fits the listing ceiling; no `commands/ralph-lite.md` exists
**so that** the mode is entered under one name whoever starts it, at the listing cost of one short description

### REQ-24: The skill carries both forms and their limits

**so that** whoever starts the mode has the whole procedure and its limits in one place

**so that** the mode is found at the moment of choice and the tier vocabulary stays consistent

### REQ-26: The recipe describes the mode, with `/goal` as a labelled fallback

## Key Decisions

- **[systems-architect] Goal mode adds no ADR; its narrowings of `dec-434` go into one dated status note at close**: the design adds no component beyond `dec-434`'s (the `goal`/`run` verbs, the spawner behind the seam, the reader's second arm, the skill); new private modules and the parser move stay inside the driver. **Why**: the architectural test names no component added, removed or re-homed. **Alternatives**: one fragment per narrowing (corpus noise for readings of one accepted record).
- **[systems-architect] N1 — the ledger's turns are the transcript's distinct-request count, not `num_turns` (`dec-434` clause 2)**: the spec's SQ-01 answer; `num_turns` (one above `--max-turns` at the cap) is kept in `WORKER_<id>.json` only; cost stays the result's `total_cost_usd`. **Why**: `dec-436` made the request count the one definition every reader shares. **Alternatives**: `num_turns` in the ledger (a second count that disagrees at the cap).
- **[systems-architect] N2 — a goal step's targets are the `FAILED` nodes of the check's own run, not `Read-only` ownership (`dec-434` clause 2)**: `GoalTargets` classifies both the check and the derived-scope run; `ERROR` nodes are never pending. **Why**: the existing ownership rule keeps the gated step's own entries as failures, and listing the check's tests in `Read-only:` could mask a protected test the check does not run; the check's own failures are the spec's definition read from ground truth. **Alternatives**: `Read-only` ownership with a goal exception; parsing test paths out of the check command.
- **[systems-architect] N3 — the worker's end reaches `record` through `WORKER_<id>.json` (`dec-434` clause 2 "whose end is the process result")**: `run` writes the parsed result object, exit code and bounds after the process exits, then calls `record` exactly as the relay does. **Why**: `record`'s arguments stay unchanged (REQ-22), one record path serves both forms, and a killed `run` can resume from disk without a second paid worker. **Alternatives**: new `record` options; an in-process record call.
- **[systems-architect] N4 — no `--bare` opt-in surface in this increment (`dec-434` clause 8)**: `run` never passes `--bare` (the spec's SQ-03 answer). **Why**: it drops the project's instructions, rules and hooks. **Alternatives**: a `--bare` option of `run` (deferred to a later increment).
- **[systems-architect] N5 — `run` is the shipped `drive` loop with the headless spawner (`dec-434` clause 4)**: `drive` gains `echo` and `observe` keywords whose defaults reproduce it. **Why**: one loop; the seam does the work it was built for. **Alternatives**: a second loop in the runner module.
- **[systems-architect] The stall is published as the `Attempts:` line's `[BLOCKED] replan:` suffix and the reconciler reads it for a goal step**: the bound is a per-step datum (`AttemptCap | GoalBudget`) read by all five readers in one step. **Why**: one rule, one writer, written in the same `record` call that makes the stall, so the driver and the reconciler cannot disagree. **Alternatives**: the reconciler re-deriving the stall from the ledger; a new `of=` token on the line.
- **[systems-architect] An unkept iteration is saved as `ITERATION_<id>.patch` and its `Files:` scope restored to HEAD**: protected changes are never restored (snapshot stop). **Why**: REQ-14's guarantee that a failed iteration's work never enters history unexamined, and a per-iteration "changed a path in scope" judgement. **Alternatives**: leave the tree for the next worker.
- **[systems-architect] `goal` takes the baseline reading and refuses a check with no pytest summary or one already met**: the reading is the first regression reference and the first prompt's "latest reading". **Why**: the relay never passes through `run`; an unreadable check would stall every loop after two paid iterations. **Alternatives**: the first `next` or `run` taking it.
- **[systems-architect] Location echo only under `run`; td-351 flipped `in-flight` for the runner's loop only**: a bare `next`'s `resume` stays byte-identical. **Why**: `tests/acceptance/test_step_loop_stops.py` pins it while passing `--base-ref`; the general remedy would edit an existing test (AC-07). **Alternatives**: echo in every verb.
- **[systems-architect] td-352 left `open`**: the runner does not need it (no foreign `HANDOFF.md` in a scaffolded goal task; the failure is loud, not unsafe).

- **[systems-architect, round 2] R2-D1 / N6 — the worker writes only its step's `Files:` and the task's `WIP.md`, by a path allow-list**: `--allowedTools` names `Read Glob Grep`, `Edit(/<path>)` per `Files:` entry (`/**` for a directory), `Edit(/.ai-work/<slug>/WIP.md)` and the two `Bash` prefixes; bare `Edit` and `Write` go, so `dontAsk` denies every other write. **Why**: one shape closes C1's tool path to the task's control files and C6's undeclared edits at the source, lives only on the worker's command line, and needs no per-slug rules in a settings file nobody removes. **Alternatives**: deny rules per task control file (eight rules per slug, every other path still writable); a worker-owned progress file (moves the spec's `## Progress record`).
- **[systems-architect, round 2] R2-D2 / N7 — the worker holds only its own pre-approvals (new finding)**: `permissions.allow` lists are combined across the user, project and local settings, and `dontAsk` runs whatever any pre-approves; this machine's user settings pre-approve `git add`, `git push`, `gh repo` and two commit forms. Before every worker `run` mirrors each scoped inherited `Bash` allow as a `--disallowedTools` deny of the same text, refuses a tool-wide `Bash` allow, a `Bash` allow whose fixed head covers the check or the resolver, and any consulted edit allow, and passes `--strict-mcp-config`. **Why**: deny beats every allow, so the mirror neutralises exactly what the allow granted while the person's deny rules, plugin and hooks stay. **Alternatives**: `--setting-sources local` or `--restricted` (drops the person's deny rules with the allows); refuse on any inherited rule (refuses nearly every machine); warn only (leaves push reachable).
- **[systems-architect, round 2] R2-D3 / N8 — a goal step's gate block is never reused**: `run_gate` reuses a written block for ordinary steps only. **Why**: a stamp or a "written by this call" rule cannot be told from a forgery by code with the same privileges, and a goal iteration's effects are already idempotent through `settled_before`. **Alternatives**: reuse only a block this call wrote (the same rule, said less plainly); a gate-only stamp (forgeable).
- **[systems-architect, round 2] R2-D4 / N9 — `run` re-checks its preconditions before every worker**: deny rules present, inherited pre-approvals neutralisable, the tree clean outside `Files:` and the task directory, the goal step's digest as at the start; before the loop a failure is `usage`, inside it a `NotStarted` (request withdrawn, `worker-not-started`, exit 4). **Why**: a change made during the loop must not reach the next paid worker. **Alternatives**: once per `run` (today); inside `record` (cannot refuse without losing the return).
- **[systems-architect, round 2] R2-D5 / N10 — undeclared edits: never committed, never restored, and they stop the terminal form before the next worker**: restore keeps D5's `Files:` scope; a `complete` `run` names any change still outside `Files:` on stderr. **Why**: REQ-14's read-only scenario keeps an iteration with a stray edit, so a stop is excluded; a whole-tree restore is the destructive act D5 bounded and would sweep an attended session's own edits in the relay form. **Alternatives**: whole-tree restore from an iteration-start snapshot; stop on any undeclared edit.
- **[systems-architect, round 2] R2-D6 / N11 — the scaffold warns `check-completes-early`, it does not require `pending=0`**: the warning fires when the baseline shows failing targets, the expectation states no `pending=0`, and its pass count is below baseline passes plus targets. **Why**: appending, refusing or an implicit `pending=0` each contradict frozen text (REQ-01's verbatim `Check:` line and its acceptance pin, REQ-16's "meets the check ... ticks the step"). Requiring `pending=0` is a promotion candidate for the next spec amendment. **Alternatives**: append, refuse, implicit pending.
- **[systems-architect, round 2] R2-D7 / N12 — the safety claim covers the worker's tool surface**: code the check runs (the worker's tests, in its own runs and the gate's) has the person's privileges and is fenced only by the scratch worktree, the fuses, R2-D3/R2-D4 and a person reading the kept commits. **Why**: the harness's rules do not reach indirect subprocess writes; claiming more would be false. **Reversal trigger**: an observed run where check-executed code changed a control file, the settings or a path outside `Files:` and it shaped a verdict or a commit — then the sandbox or a container, in its own pipeline.

## Spec Notes Carried

### Assumptions the requirement text leaves to design

Load-bearing ones first (A1, A4, A8); each is a surfaced default, not a decision the design must keep.

- **A1 — The goal's targets (REQ-13).** The spec defines them as the tests the goal's `Check:` command runs. `dec-434` clause 2 says the targets are owned by the step as `Read-only` and "read `pending` while red (the existing ownership mechanics)". Two facts the design must reconcile: (a) under today's ownership rule (`scripts/_step_loop_gate.py` docstring, `Ownership.is_pending`) a failing node owned by the *gated step's own* `Read-only:` entry stays a failure — only entries of *other*, unfinished steps make a node pending — so goal mode changes the rule for goal steps rather than reusing it; (b) if "targets" were every `Read-only:` entry, a protected test outside the check's run that an iteration breaks would read `pending` and be masked from the gate and from the check's counts. The spec requires the safer reading; the design may realise it through `Read-only` ownership provided (b) cannot happen.
- **A2 — The working tree after a non-progressing iteration (REQ-14).** Restored to the last commit, or left in place for the next worker: design's call. Either way the diff is kept as a patch named by request id and the next prompt names it (REQ-12). Today's `TREE_SNAPSHOT_<id>.patch` stops the loop until a person deletes it (`commit-disturbed-tree`); the goal-mode patch must not stop the loop.
- **A3 — The reading before the first iteration (REQ-14).** Taken by `goal` at scaffold time or by the first `next`; the spec pins only that a first iteration's regression is judged against it.
- **A4 — Which count is `turns` (REQ-11).** The spec keeps one count: the transcript's distinct requests, the definition the dogfood pipeline's REQ-12 made the only one (`hooks/_agent_transcript.py`, `request_count`). `dec-434` clause 2 reads "whose turns and cost are the result's fields", and the spike's probe found `num_turns` reads one more than `--max-turns` at the cap. Registered divergence: the design may additionally record `num_turns` under a new optional key; the falsifier readings (AC-09) use `turns`. A top-level transcript an assistant record of which lacks `requestId` yields no count, never a guessed one.
- **A5 — The per-iteration bounds (REQ-07).** The values of the turn bound and the dollar fuse and where they come from (options of `run`, plan fields, or defaults stated in `--help`), and the spelling of the `--bare` opt-in. `max_turns` in the ledger is the turn bound passed to the worker, never an agent definition's `maxTurns`.
- **A6 — `request.attempt_cap` for a goal step.** The stall cap (2) or the `Iterations:` value; the spec pins only that `attempt` never exceeds `Iterations:` (REQ-17).
- **A7 — Mixed plans and review markings.** A plan holding both goal and ordinary steps, and a goal step carrying `review: force` or `tier: H`: the scaffold writes neither; refuse or define is design's call. REQ-17 pins only a goal plan's budget.
- **A8 — `run` refuses a plan with no goal step (REQ-04).** Chosen as the conservative, reversible default: a headless, paid, unattended loop runs only where `goal` wrote the deny rules. `dec-432`'s reversal trigger may later open `run` to Standard and Full plans; that is a later decision. Whether `run` also refuses when the deny rules are missing from `.claude/settings.local.json` is design's call.
- **A9 — The stop cause for a protected-path change (REQ-15).** Reuse `commit-disturbed-tree` or add a cause; the spec pins the outcome, the exit and the `evidence`.
- **A10 — The deny rules (REQ-02).** Rule syntax (`Edit(...)`, `Write(...)`, glob anchoring relative to the settings file) to be verified against the live permissions docs at design, per the cross-agent convention on external APIs. The default protected set is `dec-434` clause 6's policy. Whether the default set also rides in `Read-only:` (glob entries versus the prefix ownership `Read-only:` uses) is design's; REQ-01 puts only the `--protect` paths there. In a managed project whose own source lives under `skills/` or `agents/`, the default set refuses goals there (REQ-03); whether the default set stays fixed or narrows to what exists is design's call.
- **A11 — Abnormal worker ends.** A worker that exits with no result object but left a transcript naming its request meets `record`'s existing `not-started-but-ran` refusal (`run` then exits 4 per REQ-08's message path or design's refinement). A `run` killed mid-iteration and restarted meets a reissued request (`next` prints it again with `reissued: true`): the design must not start a second worker blindly for a request whose first worker may have run; commit idempotency on the trailer already holds.
- **A12 — Progress record growth.** The prompt's ceiling is 16,000 characters (`_step_loop_render.py`); which lines of `## Progress record` survive when it outgrows the slot is design's (most recent first is the obvious default).
- **A13 — The dollar-fuse stop.** A worker stopped by `--max-budget-usd` reports `subtype: error_max_budget_usd`; the ledger's stop-reason set is closed (`completed`, `turn-cap`, `blocked`, `conflict`, `partial`, `no-marker`); the mapping is design's.
- **A14 — The spawn counter and headless workers.** A `claude -p` worker is a top-level session, not an Agent-tool spawn (no SubagentStart, no spawn-result row); the counter is not expected to see it. Out of scope; FC-06 bounds the live run from its own ledger.
- **A15 — Module allowances (the brief's Health Guards).** `scripts/_step_loop_record.py` (499 lines) gains at most what the review-return branch needs and no more; new logic goes in new or roomier modules; `scripts/step_loop.py` (389) stays under 400 or the verbs move to the CLI module; `reconcile_pipeline_state.py` (711) and `compose_handoff.py` (797) are not landing sites. The cap's goal-mode reading lands in all five readers at once — `_step_loop_state.py`, `_step_loop_action.py`, `_step_loop_cli.py`, `_step_loop_record.py`, `_step_verdict.py` (`ATTEMPT_CAP` at `scripts/_loop_fields.py:284`) — or not at all (`.ai-work/step-loop-dogfood/HANDOFF_intake.md § 5` item 29). The help text's "There are exactly these three verbs" changes with the two new verbs.
- **A16 — Ledger rows in scope.** td-351 (`then` and `stop.resume` drop the caller's `--base-ref`): REQ-06 closes it for the loop `run` owns. Whether `next`'s own `then` and `resume` also echo the caller's options — the row's general remedy, which also touches `skills/step-loop/SKILL.md` — is design's call; the in-session form (REQ-21) inherits td-351 unless it does. td-352 (`record` exits 1 when the stop handoff cannot be written over a hand-written `HANDOFF.md`): design's call; a goal scaffold writes no `HANDOFF.md`, so `run` meets it only if a person placed one.
- **A17 — Worker routing and context.** `--model` is the request's model (sonnet for an implementer step; the scaffold sets no tier). No `--agent` (`dec-434` names none, and `maxTurns` under `--agent` is unstated in the docs). The worker's working directory is the repository root; `inject_subagent_context` and `remind_task_brief` do not fire for a process worker; the plugin's SessionStart and UserPromptSubmit hooks do (the fixed per-iteration cost AC-09 measures).
- **A18 — The hook-latency declaration holds only if the reminder's path is untouched.** The declaration in `### Footprints Not Measured` assumes the new top-level lookup is reached only by an explicit call from the driver, never as a fallback inside the reminder's own lookup. If the design puts it on the reminder's path, convert the declaration into a bounded row read with `/usr/bin/time -p <registered-hook-command...>` against the dogfood pipeline's bounds (0.2 s main-session payload, 0.3 s subagent payload).
- **A19 — Unregistered footprints go stale.** FC-05 to FC-07 are not in `.ai-state/FOOTPRINTS.md`, so any tracked change outside `.ai-state/` stales them (FP04): their final readings come after the last tracked change. FC-06 and FC-07 read the live run's own ledger (`<live-slug>` is the live run's task slug).
- **A20 — Non-pytest checks.** The gate reads pytest summaries only (`dec-434` clause 8). A non-pytest command passes the `Check:` grammar, reads as no run (red) every iteration, and stalls at two; the design may refuse it at scaffold. The skill and the recipe state the limit (REQ-24, REQ-26).
- **A21 — An already-met goal.** If the check is met before the first iteration, an empty-diff iteration is never committed (REQ-14), so REQ-16 never fires; the design may complete at the first `next` from the pre-iteration reading or refuse at scaffold.
- **A22 — Light reviews on goal steps** are out of scope for this increment.
- **A23 — Falsifier comparator (AC-09).** "A hand-run Lightweight task's turns" is a named, comparable task's orchestrator turns read from its session transcript or calibration row; "fixed cost" is the cost of an empty iteration with the same options in the same worktree; the ratio compares iterations × fixed cost with the rest of the ledger's total. `dec-434`'s falsifier fires at more than three to one, judged over the first three runs.
