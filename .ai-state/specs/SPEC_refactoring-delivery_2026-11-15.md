## Feature Summary

The refactoring skill's delivery to marked delegations is built and silent; the move that drops the preload is held.

What ships is the interim state, plainly: both agent definitions (the implementer and the test-engineer) still preload the refactoring skill, the new delivery stays silent for them, and no real spawn changed. The move is built, proven on copies of the plugin and not applied. It is the plan's step 29, held for the user. No model session and no eval run was started by this pipeline.

Before this:
- The implementer and the test-engineer preloaded `skills/refactoring/SKILL.md` on every spawn (a body of 4,184 tokens, over 557 implementer and 95 test-engineer spawns in 90 days), although only a delegation of a step tagged `[Phase: Refactoring]` needs it.
- `dec-504` had kept every preload because no eval kit could show that a lighter delivery keeps the skill's semantics, and the model-initiated alternative (a pointer the model follows) fails at the trigger.

Now, in the interim state:
- **A delivery exists and is silent.** `hooks/_skill_delivery.py` decides, for each Agent call, whether a delegation to either role carries the marker `[Phase: Refactoring]` in its own words (outside code spans, fenced blocks and quoted passages), or is a step-loop request for a tagged step. The single prompt-rewrite emitter, `hooks/inject_subagent_context.py`, gained a trailing slot. When a role's definition no longer lists the skill among its preloads, the emitter appends the skill's body, whole and unaltered, as one labelled block with its base directory, after the delegation's own words. While a definition still preloads the skill (today), the delivery adds nothing.
- **It fails open and leaves proof.** A failed delivery never stops a spawn: it appends a notice, writes a `skill_delivery` row to the observation log where a log serves the project, and writes a line to stderr. A delivered spawn's own record carries the label and a digest of the body, so a check can show arrival without asking the agent.
- **The move is a declared tool.** `scripts/refactoring_move.py --to {preloaded,delivered}` sets both definitions to one state (two `skills:` entries plus the state-dependent sentences and the Codex wrapper passage), is reversible and refuses drift by site. The acceptance binding and the eval's arm builder use the same tool, on copies only.
- **The marker has one definition.** The plan reader keeps the grammar under the public name `REFACTORING_TAG_PATTERN`; the delivery re-exports it.
- **Guidance carries the marker.** The delegation guidance for the two roles and the pre-refactor dispatch guidance tell the orchestrator to carry the step's heading, marker included, in the delegation's own words. A hand delegation that omits the marker is not served after the move; this residual is accepted and surfaced (see Held and Spec Question Q2).
- **The eval can run the paired comparison, at no cost to the ordinary one.** The adherence eval gained a second arm axis, `refactoring-delivery`, whose arms `preloaded` and `delivered` are copies of the plugin set by the shared move tool. Both roles have a refactoring pool of 6 tasks (two templates, three variants each) outside the default pool, graded from the end state a session leaves against the refactoring skill's verification checklist, never from the role's own account. Each arm is proven from the proof spawn's own transcript before any of its tasks is scored. The paired run runs to its end under `praxion-evals-adherence <checkout> --role <role> --axis refactoring-delivery --required-pairs N`; continuing and calibrating it are refused; the ordinary comparison's runs, results files and reports read exactly as before. All of this is proven over stand-in sessions (52 outer-loop nodes drive the real console entry); only a paid run can show what the harness does with a rewritten prompt of about 12,100 characters.
- **No always-loaded file was touched.** Always-loaded tokens read 19,988 against the 25,000 ceiling.

What the user decides next is in the Held section: the size probe, the paired run (its size, its pass criterion, the judge) and the move itself.

## Key Decisions

- **The skill reaches a marked spawn through a trailing segment of the single prompt-rewrite emitter, not through `SubagentStart`** (`dec-514`).
  - Evidence: the hooks reference (read 2026-11-13) shows `SubagentStart` input carries the agent's id and type but no delegation text, so it cannot see the marker; a note written at `PreToolUse` has no documented key matching it to its spawn under same-role fan-out. `PreToolUse` on the Agent tool sees `tool_input.prompt`, is decided per call (safe under concurrency), and is the shipped, observed channel of the worktree briefing.
  - Rejected: `SubagentStart` `additionalContext` (blind to the marker; two strings with no guaranteed order), a second `updatedInput` emitter (reopens the undocumented chaining of several emitters, `dec-266`), and a pointer the model follows (fails at the trigger).
  - This departs from the channel the user's item named, which the item itself allowed once the payload was verified. The departure was surfaced to the user (Q1).
  - Cost: the skill arrives inside the first user turn, exposed to compaction with the task, instead of in a system-reminder slot.
  - **Falsifier:** in the size probe or the paired run's delivered arm, the spawn's own first user message does not hold the label line and the whole body. **Steelmanned runner-up:** `SubagentStart` delivery reading the spawn's own first message from its transcript, two labelled strings each under the cap, whose one premise (the first message is filed before the event fires) can be checked at no cost. **Reversal trigger:** the probe or the proof fails on the rewritten prompt's length, or Claude Code documents an `updatedInput` limit below the block's 12,100 characters.
- **The delivery reads the role's own `skills:` list to know the state** (`dec-514`). The list is what the harness itself reads, so the delivery and the harness cannot disagree and the move is pure frontmatter. A configuration flag the move flips (a second source that can drift) and always delivering with two copies in the interim (violates REQ-09 and REQ-10) were rejected. An unreadable definition means the delivery fails, loudly.
- **The step-loop route needs no change to the driver** (`dec-514`): the delivery reads the step heading from the rendered request the driver's pointer prompt names. The driver adding the marker to its pointer prompt breaks a pinned three-line contract, and the description is limited to 40 characters. The coupling to the driver's pointer grammar and its `<step>` element is explicit, and tested against the driver's own golden fixture.
- **The move is a declared, bidirectional, drift-refusing tool, held** (`dec-514`). Landing the definition sentences in the interim would break REQ-10 (the definition text is part of every spawn's start), and hand edits at the move would give three drifting copies. Its Codex passage is worded host-scoped ("on a host with no spawn-time delivery, such as Codex, ..."), so on Claude Code it is inert and a failed delivery is covered by the deterministic notice, not by a sentence a model may or may not follow.
- **The marker has one definition, the plan reader's** (`dec-514`, and the implementer's choice in step 4): `REFACTORING_TAG_PATTERN` is the same object as the private regex, re-exported by the delivery as `MARKER_PATTERN` through a guarded import. Copying the regex into the hook (two grammars) and lifting it into a new module (a file for one line) were rejected; the plan reader's purity guard forbids a new import. If the import fails, the interim is unaffected (the preload check comes first) and an end-state spawn fails loudly as `grammar-unavailable`.
- **A second arm axis on the role eval, not a main-session move kit** (`dec-513`). The implementer and the test-engineer already run with `omitClaudeMd: true`, so the eval's existing `full` and `lean` arms do not differ for them, and the moves package grades main sessions and has no change type for a definition's preload. The axis keeps the inherited-context axis as the default; the refactoring tasks are graded from the end state, reusing the moves graders' "end state, never its words" shape. The refactoring pool is a directory of its own, outside every default pool (the architect's ruling B), so no default plan or pin moves.
- **The paid loop is parameterised by one `AxisRun` value** (`dec-513`, amended by the ruling of 2026-11-14). After step 22 a second architect found the plan had built the paired run's pieces and wired none of them into the paid loop. The loop, the pairing, the report and the dry run now read positions, never arm strings. Every effectful axis difference (plan, stage, build, proof, assess, catalog, refusals) lives in one record chosen once per run. Rejected: a `match axis` at about eight sites, a second loop module (duplicates about 300 lines of stop, retry, checkpoint and spend logic), renaming `Pair` (a wide ripple through frozen wording). **Falsifier:** a third axis needs a field the record lacks, or the default axis's results change by a byte when routed through it. **Reversal trigger:** the record grows past about ten fields, or an axis needs per-task dispatch. The requirement text governs over the ruling's design notes where they differ: a stopped paired run blocks a fresh run of its own axis only.

## Requirements

Requirements are pipeline-local; never cite their ids in code, tests or docstrings. The text below is the behavioural specification as it stood at the end: 23 requirements, REQ-20 reworded and REQ-22 and REQ-23 added by the paid-path ruling of 2026-11-14 (Spec Question SQ-04 below); the spec extract's digest at the end is `sha256:1b7c9bfde7e1`. Each requirement is verified by outer-loop scenarios, by unit tests, or, where the text is markdown guidance a model follows, by the verifier's judgment (listed after the requirements).

### Terms

- **The marker** is `[Phase: Refactoring]`. It is recognized whatever the letter case and spacing inside its brackets, as plans already recognize it in a step heading.
- **A tagged step** is a plan step whose heading carries the marker.
- **Carries the marker**: the marker appears in the delegation's own words, outside a code span, a fenced block and a block-quoted passage.
- **A marked delegation** is a delegation to the implementer or the test-engineer that carries the marker, or a step-loop driver request for a tagged step (REQ-02).
- **The skill's text** is the body of the refactoring skill, everything after its metadata header, as shipped in the same installation.
- **Interim state**: a role's definition still preloads the refactoring skill. **End state**: neither definition does. Going from one to the other is **the move**.
- **The delivery** is whatever puts the skill's text into a marked spawn. This spec does not choose it.

### Observable Surface

- `[Phase: Refactoring]`: the refactoring phase marker that plan step headings already carry
- `/praxion:step-loop`: the step-loop driver, which spawns the implementer (and the verifier) for each plan step
- `praxion-evals-adherence`: the adherence eval's entry
- `--dry-run`: the adherence eval's flag that prints the sessions a paid run would launch, and spends nothing
- `python3 scripts/measure_token_budget.py --json`: the always-loaded and listing token instrument, the registry's command
- `python3 -c "import os, sys; sys.path.insert(0, 'scripts'); from measure_token_budget import count_tokens; body = open('skills/refactoring/SKILL.md', encoding='utf-8').read().split('\n---\n', 1)[1]; print(count_tokens(body, os.environ['ANTHROPIC_API_KEY']))"`: the same instrument's tokenizer count applied to the refactoring skill's body, run from the repository root; it starts no session
- `python3 scripts/check_agent_prompt_size.py --json`: the prompt-size instrument, the registry's command
- `python3 scripts/measure_startup_payload.py agent:<name> --strict-mcp-config --plugin-dir <checkout> --json`: the live startup probe, the registry's command; each run starts a real session

### REQ-01: A marked spawn holds the skill from its first turn

**When** the implementer or the test-engineer is spawned with a marked delegation
**and** that role's definition does not preload the refactoring skill
**the system** places the skill's text in the spawned agent's context before its first turn, without the agent calling a tool, reading a file or choosing to load anything, in every project where Praxion's roles are installed, managed or not
**so that** a tagged step's verification authority is present from the start and never depends on a model deciding to fetch it, which the evidence shows fails at the trigger

### REQ-02: The step-loop driver never hands a tagged step over unmarked

**When** the step-loop driver issues a spawn request to the implementer
**the system** treats that spawn as marked exactly when the heading of the step the request is for carries the marker, even when the short text of the request only points at the request it rendered; it treats a request for an untagged step as unmarked, even when other text the request holds quotes the marker
**so that** a tagged step never reaches the implementer unmarked through the driver, and an untagged step never pulls the skill

### REQ-03: The orchestrator's own delegation of a tagged step is marked

**When** the orchestrator delegates a tagged step to the implementer or the test-engineer by hand
**the system**, through the delegation guidance it ships for those two roles, has the delegation carry the step's heading, marker included, in the delegation's own words
**so that** following the guidance yields a marked delegation and the skill arrives without anyone pasting its text

### REQ-04: Every delegation in the pre-refactor sub-pipeline is marked

**When** the orchestrator dispatches the pre-refactor sub-pipeline, every step of which is tagged
**the system**, through its shipped dispatch guidance, has every delegation of those steps to the implementer or the test-engineer carry the step's heading with its marker, the test-engineer's characterization-tests-first step included
**so that** the restructuring discipline reaches each role in that sub-pipeline just as the preload delivers it today

### REQ-05: An unmarked spawn receives none of the skill

**When** the implementer or the test-engineer is spawned with a delegation that is not marked
**and** that role's definition does not preload the refactoring skill
**the system** adds none of the skill's text to the spawn
**so that** the spawns that do no refactoring, most of them, stop paying for it

### REQ-06: Quoting the marker does not mark a delegation

**When** a delegation to either role contains the marker only inside a code span, a fenced block or a block-quoted passage
**the system** treats the delegation as unmarked
**so that** a delegation that discusses, quotes or relays a plan does not pull the skill by accident, and the marker keeps one meaning

### REQ-07: No other role receives the skill

**When** any role other than the implementer and the test-engineer is spawned, including the verifier the step-loop driver spawns for a tagged step
**the system** adds none of the skill's text, even when the delegation carries the marker
**so that** the delivery's cost lands only where the skill is used today

### REQ-08: The skill arrives whole and identical

**When** the skill's text is delivered to a spawn
**the system** delivers the body of the refactoring skill shipped in the same installation as one unbroken passage: every line, in order, unaltered, never a summary, an excerpt or a part, with no other text inside it. Any text the delivery adds around the passage (REQ-15, REQ-21) stays outside it. It does so even though that body (11,759 characters) is longer than the 10,000-character limit some delivery channels place on a single piece of text. When the whole cannot be delivered, it delivers none of it and records why (REQ-14)
**so that** a marked spawn receives everything the skill says, later edits to the skill reach the next marked spawn, and nothing is cut to fit a channel

### REQ-09: A marked spawn holds exactly one copy

**When** a marked spawn of either role starts, or is later resumed
**the system** leaves it holding exactly one copy of the skill's text: the delivery adds none while the role's definition still preloads the skill, and none again on a resume
**so that** a marked spawn pays for the skill once, never twice

### REQ-10: The interim state changes no real spawn

**When** either role is spawned while its definition still preloads the refactoring skill
**the system** gives the spawn exactly what it gives it today for the same delegation, marked or not, with nothing added and nothing removed
**so that** this pipeline can merge the interim state without the user's go, and no real spawn changes before the move

### REQ-11: The end state preloads no refactoring skill

**When** the move has been applied
**the system** has neither definition preload any part of the refactoring skill, while each still preloads every other skill it preloads today, and REQ-01, REQ-05 and REQ-09 hold for every real spawn of either role
**so that** each unmarked spawn saves at least the skill body's tokens and each marked spawn still holds the skill once

### REQ-12: Concurrent spawns each get their own answer

**When** several spawns of the same role start at once, some marked and some not
**the system** gives each spawn exactly what its own delegation calls for
**so that** a fan-out never swaps, duplicates or drops a delivery

### REQ-13: The delivery adds and never replaces

**When** the skill's text is delivered
**the system** leaves the delegation's own words, and everything else the spawn receives at its start today, present and unchanged: its definition, its other preloaded skills, its startup text and the briefing lines it is given now
**so that** the delivery cannot cost a spawn any of its existing context

### REQ-14: A failed delivery never stops a spawn and never fails silently

**When** the delivery cannot complete because the skill cannot be read, the spawn's input is malformed, or the delivery errors or runs out of time
**the system** still starts the spawn with its delegation unchanged, never blocks or refuses it, and records the failure where a later check can find it
**so that** a broken delivery never stops work and is noticed

### REQ-15: Arrival is provable from the spawn's own record

**When** the skill's text is delivered to a spawn
**the system** leaves words in that spawn's own record that a check can match, showing the text arrived by this delivery, and leaves no such words in a spawn that did not receive it
**so that** the eval and the liveness checks can prove arrival without asking the agent

### REQ-16: Shipped sentences about the skill's arrival stay true

**When** an agent or the orchestrator reads any shipped text that says how the refactoring skill reaches a step or a role: the two definitions, the planner's definition, the planning skill's refactoring phase and its delegation guidance, the refactoring skill's own entry points, and the always-on coordination rule
**the system** states only what is true in the state it ships in. In the interim the skill is preloaded; in the end state it arrives on a marked delegation, and no text says it is always loaded
**so that** no agent is told the skill is present when it is not, or told to fetch what has already arrived

### REQ-17: The Codex and Cursor exports stay true

**When** either definition is exported for Codex, or the rules are exported for Cursor
**the system** lists the refactoring skill among an exported definition's preloaded skills only while that definition preloads it. Once it does not, the Codex export names the refactoring skill as the verification authority of a tagged step and tells the agent to read it when its delegation carries the marker, since no delivery reaches a Codex agent. The Cursor export's sentences about the marker stay true
**so that** an assistant without spawn-time deliveries falls back to a pointer to the skill, never to nothing

### REQ-18: The eval kit holds refactoring-mode tasks for both roles

**When** the adherence eval is dry-run for the implementer or for the test-engineer
**the system** lists at least two refactoring-mode tasks of that role among the sessions a paired run of the move would launch, each delegated with the marker in its own words. A dry run of the eval's ordinary comparison lists exactly the sessions it lists today, for these two roles as for every other. Neither dry run starts a session or spends anything
**so that** a paired run can later show whether the skill's semantics arrive, while every ordinary run stays comparable with the runs before it

### REQ-19: Refactoring-mode tasks are graded from the end state

**When** a refactoring-mode task is graded
**the system** judges what the task left behind, never the agent's own account of it, against the refactoring skill's verification checklist. For the implementer: the tests still pass, behaviour is unchanged, every call site is re-wired, and no dead code and no transitional shim remains. For the test-engineer: characterization tests exist before any structural change and pin behaviour through the public surface
**so that** a pass means the skill's discipline was applied, not described

### REQ-20: A paired run of the move is ready but not run

**When** a paired run of the move is dry-run
**the system** names the sessions it would launch: the same refactoring-mode tasks, once with the role preloading the skill as today and once with the role after the move receiving it by marked delivery. This pipeline launches no paid session; the paired run is started only on the user's go, by the command the run card names, and that command runs it to its end (REQ-22)
**so that** the user can approve the run with a run card, and then the move, on evidence

### REQ-21: Everything the skill links to stays reachable

**When** the skill's text is delivered to a spawn
**the system** lets the spawned agent reach every file and section the skill's body links to, its own reference material and the other skills it points to, exactly as a spawn that preloads the skill can. The links resolve against the same installation the body came from, wherever that installation keeps the skill: a checkout of this repository, or the plugin's installed copy that managed and unmanaged projects use. The body itself is not rewritten
**so that** a marked spawn loses none of the material the skill reaches on demand, and no link silently fails by resolving against the project's own directory

### REQ-22: A paired run of the move scores each arm from the end state

**When** a paired run of the move runs for the implementer or the test-engineer
**the system** builds one copy of the plugin as it is today and one as the move leaves it, and before any task of an arm is scored shows that a marked spawn in that arm holds the refactoring skill exactly once and by that arm's own way: by preload in the first, by delivery in the second. An arm that cannot be shown so has none of its tasks scored, and the report says why. Each task then runs once in each shown arm, in a repository that holds the task's starting state and none of the material its grade is decided by. Each session is graded from what it leaves in its repository against the role's refactoring checklist and the role's ordinary checks, never from the role's own account, and the record of each session says whether the skill reached the role that arm's way. The report gives, for each role and each check, how the arm after the move compares with the arm before it over the tasks that ran in both, and says for each check whether the run holds enough evidence to judge it
**so that** the user decides on the move from a result that the run card's command produces, and an arm that does not differ as claimed spends nothing on tasks

### REQ-23: The paired run declines what it does not support, and the ordinary comparison is unchanged

**When** the operator asks a paired run of the move to continue a stopped run, to calibrate, or to run an arm of the ordinary comparison
**the system** refuses before it writes or launches anything, naming the option, and for a stopped paired run says to close it and start a fresh one. Closing, listing and reporting a paired run work as for any run, and every run, results file and report of the ordinary comparison reads, lists and reports exactly as before
**so that** an operator is never left with a half-supported run, and the paired run costs the ordinary comparison nothing
