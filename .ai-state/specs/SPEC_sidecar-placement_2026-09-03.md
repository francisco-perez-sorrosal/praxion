## Feature Summary

Praxion assumes it owns the git tree it manages. That assumption breaks for an operator running Praxion on someone else's repository -- their own onboarding write would be foreign traffic the team never asked for. This feature adds two independently-mergeable milestones. **P0** makes git-hook installation observe the repository's existing hook configuration and *compose* with it: an occupied `pre-commit` slot gets a wrapper that runs the team's hook first and Praxion's gates second (never displaced); a foreign `core.hooksPath` (husky/lefthook-style) gets a Praxion wrapper directory created inside the git *common* directory and chained in, with no tracked file touched; a SessionStart self-heal restores the chain if a package-manager `prepare` script re-points it. **P1** adds `--placement sidecar`: under it, `.ai-state/` and the operator's private Claude config keep their exact on-disk path contract, but the git repository that owns them moves to a per-operator sidecar under `${PRAXION_SIDECAR_ROOT:-~/.praxion/sidecars}/<project-id>/`. The path is projected in via relative symlinks hidden in a Praxion-owned `.git/info/exclude` block, so `git status`/`git add -A` in the project show nothing Praxion-related.

The load-bearing architectural decision, reached after the initial design was **falsified live** by Claude Code's worktree isolation (which refuses a `Write`/`Edit` on a lexically-in-worktree path whose realpath escapes the worktree, with no sanctioned exemption), is **Option F -- the state mount** (`ARCH_WT_RULING.md § 2`): every project checkout -- main and every linked worktree, uniformly -- materialises the sidecar as a real directory at `<checkout>/.praxion-state/`, a `git worktree` of the sidecar repository on a per-checkout branch (`main`, or `wt/<name>` for a linked worktree); the four shadows become relative symlinks pointing *into* that mount. This installs an **in-checkout realpath invariant** -- every path Praxion asks an agent to write resolves inside the checkout the session is running in -- which is what makes both of Praxion's existing containment guards (`worktree_guard.py`, `project-root.ts`) correct **without modification**. The cost is a merge step (a worktree's sidecar branch must reach the base branch before its drafts are visible), which a later revision (`ARCH_WT_RULING.md § 13`) turned from an ordering constraint an operator could forget into a **convergence step** run idempotently from three channels (the project `post-merge` finalize chain, the SessionStart heal, and `/merge-worktree` explicitly) -- a manual merge, a GitHub squash merge, and a hard reset all converge.

## Requirements

### P0 — hook chaining

- **REQ-01** — When Praxion installs git hooks, and `core.hooksPath` is unset and the target hook slot is empty, the system installs today's plain symlink (`post-*`) or inline script (`pre-commit`) unchanged, so that existing managed projects see no diff and no new failure mode.
- **REQ-02** — When Praxion installs git hooks, and `git config core.hooksPath` names a directory Praxion does not own, the system creates a Praxion wrapper directory inside the repository's git **common** directory, records the observed value as the delegate, installs chaining wrappers there, and re-points `core.hooksPath` at the wrapper, so that Praxion's hooks fire in a husky- or lefthook-managed repo without editing any tracked file.
- **REQ-03** — When Praxion installs the pre-commit hook, and the slot is occupied by a non-Praxion hook, the system installs a wrapper that invokes the pre-existing hook first (preserved at `<name>.pre-praxion`) and only then Praxion's own gates, so that a team's pre-commit-framework gate keeps running instead of being displaced.
- **REQ-04** — When a chained pre-commit runs, and the delegate exits non-zero, the system aborts the commit with the delegate's exit code and does not run Praxion's gates, so that the team's gate stays authoritative and its failure is never masked.
- **REQ-05** — When a chained `post-merge` / `post-commit` / `post-checkout` runs, and the delegate exits non-zero, the system prints a one-line notice, continues with Praxion's finalize chain, and exits 0, so that the finalize chain's established non-blocking contract is preserved.
- **REQ-06** — When a Claude Code session starts, and a Praxion wrapper directory exists but `core.hooksPath` no longer points at it, the system re-points `core.hooksPath` at the wrapper, updates the recorded delegate only when the observed value is a foreign directory, and prints one line, so that a package manager's `prepare` script cannot silently disable Praxion's hooks.
- **REQ-07** — When the self-heal runs, and the observed `core.hooksPath` already equals the Praxion wrapper directory, the system performs no write, so that repeated sessions cannot oscillate the configuration.
- **REQ-08** — When the self-heal would record a delegate, and that delegate resolves to the Praxion wrapper directory itself, the system refuses the write and warns, so that a wrapper can never delegate to itself and recurse.
- **REQ-09** — When a chaining wrapper resolves its delegate, and the recorded delegate value is relative, the system resolves it against the **current** working tree's root, so that a linked worktree runs its own copy of the team's hooks exactly as bare git would.
- **REQ-10** — When `core.hooksPath` is set but cannot be read or resolved to a directory, the system refuses to install or heal the chain, warns once naming the observed value, and leaves existing wiring untouched, so that an unrecognized configuration is never guessed at.
- **REQ-11** — When install or upgrade runs against a repository whose chain is already current, the system makes no filesystem or config write, so that the operation is idempotent and safe to re-run.
- **REQ-12** — When the operator runs the hook installer in status mode, the system reports the observed hooks-path state, the delegate, and per-slot ownership, and names any slot in which Praxion's hooks cannot fire, so that a silently-inert install is diagnosable without reading `.git/` by hand.
- **REQ-13** — When the operator runs the hook installer in uninstall mode, the system restores the recorded pre-Praxion `core.hooksPath` (or unsets it) and re-installs the delegate hooks in their original slots, so that Praxion's presence in a team repo is fully reversible.

### P1 — sidecar placement

- **REQ-14** — When onboarding is invoked with `--placement sidecar`, and the resolved mode is not `existing`, the system exits with a usage error naming the legal combination, so that placement and mode cannot be combined into a state with no meaning.
- **REQ-15** — When onboarding runs with `--placement sidecar`, and no sidecar exists for the derived project identity, the system creates one under `${PRAXION_SIDECAR_ROOT:-~/.praxion/sidecars}/<project-id>/`, initializes it as a git repository with no remote, and writes `praxion-sidecar.yaml`, so that all clones and worktrees of one project converge on one state store.
- **REQ-16** — When the sidecar is linked into a project, and a shadow's target slot is absent, the system creates a symlink to the sidecar path and adds the path to a Praxion-owned block in `.git/info/exclude`, so that the shadow is invisible to `git status` and `git add -A` without editing `.gitignore`.
- **REQ-17** — When the sidecar is linked, and a shadow's target slot holds a real file or directory, or a symlink pointing somewhere other than this sidecar, the system refuses to touch that slot and reports it, so that operator content is never overwritten by linking.
- **REQ-18** — When any consumer asks which git repository owns `.ai-state/`, the system returns one of `in-repo`, `sidecar-owned`, `dangling`, or `foreign` together with the paths that variant carries, so that no consumer re-derives placement from a bare path.
- **REQ-19** — When the resolver returns `dangling` or `foreign`, and the caller is a state-mutating script, the system refuses to write and reports the resolved target, so that a broken or third-party link is never silently written into.
- **REQ-20** — When the finalize chain runs in a sidecar-placed project, and draft ADRs are present on `main`, the system promotes them, performs the rename and staging **in the sidecar repository**, and rewrites draft-id citations in both the sidecar's `.ai-state/` and the project's `docs/`, `ROADMAP.md`, and `.ai-work/`, so that promotion works across the two-repository split without losing the project-side citation scope.
- **REQ-21** *(revised — reason changed, observable unchanged)* — When the finalize chain runs in a sidecar-placed project, the system does not run `reconcile_ai_state.py` or `check_squash_safety.py` **against the project repository** and says so once, so that reconcilers do not operate on a repository that does not own `.ai-state/`. (Under the ruling these reconcilers are *not* dead: they run against the state mount at merge-back — REQ-38.)
- **REQ-22** — When the finalize chain has finished mutating sidecar state, and the manifest's autocommit policy permits it, the system commits the sidecar with a generated message, so that project intelligence is versioned without the operator remembering to commit it.
- **REQ-23** — When a Claude Code session stops, and the sidecar working tree is dirty and the autocommit policy is `on-finalize-and-stop`, the system commits the residue, so that state written outside a git event is not left uncommitted.
- **REQ-24** — When any autocommit runs, the system commits only the sidecar repository, so that project commits remain human-owned.
- **REQ-25** — When the operator adds a sidecar remote, and the URL's host differs from the project origin's host, the system refuses unless `--allow-foreign-host` is given, so that work-machine project intelligence cannot be pushed outside its trust boundary by accident.
- **REQ-26** *(revised)* — When a new git worktree is created in a sidecar-placed project, the system materializes that worktree's **state mount** — a sidecar worktree at `<worktree>/.praxion-state` on branch `wt/<name>`, branched from the base checkout's sidecar branch — and then its shadow symlinks, driven from the `post-checkout` hook with the SessionStart heal as an idempotent backstop, so that a pipeline worktree is immediately usable **and writable through the Write/Edit tools**.
- **REQ-27** — When a Claude Code session starts in a sidecar-placed project, the system re-runs the link step as a self-heal and announces the placement and sidecar location, so that the operator always knows where project intelligence accumulates and a partially-linked tree repairs itself.
- **REQ-28** *(revised — the code change it described is deleted)* — When a `Write` or `Edit` inside a pipeline worktree targets `.ai-state/`, `CLAUDE.local.md`, a shadowed `CLAUDE.md`, or `.claude/settings.local.json`, the path resolves **inside the session worktree** (through the state mount), so both Claude Code's worktree isolation and `worktree_guard.py` allow it **without modification**; a write targeting the main checkout or a sibling worktree is still blocked with exit 2, so that the guard's original cross-worktree hazard remains covered by unchanged code. *(amended 2026-09-03, `ARCH_WT_RULING.md` § 15 — file-shadow tool-write caveat)* This clause holds without qualification for `.ai-state/` (a directory shadow): a `Write`/`Edit` through it succeeds. For the three **file** shadows (`CLAUDE.local.md`, a shadowed `CLAUDE.md`, `.claude/settings.local.json`), the harness additionally refuses a `Write`/`Edit` whose target is a file-level symlink even though its realpath resolves inside the checkout — the tool must target the mount path (`.praxion-state/<name>`) directly, and the harness's own refusal message redirects there. Reads and Claude Code's own config *loading* through the file shadows are unaffected — a symlinked `CLAUDE.local.md` and a symlinked `.claude/settings.local.json` both load normally.
- **REQ-29** *(revised — the second realpath root is deleted)* — When the dashboard resolves an artifact path under sidecar placement, the resolved path stays inside the project root by construction (it lands in the state mount), so both of `project-root.ts`'s containment checks pass unchanged and a path escaping the project root is still rejected; the only change is that the resolved-path **allowed-artifact-root** allowlist recognises the `.praxion-state/.ai-state` prefix, so that mounted state is readable without introducing an environment-supplied second root.
- **REQ-30** — When onboarding writes Praxion `CLAUDE.md` blocks, and the project has a tracked `CLAUDE.md`, the system writes every block to the shadowed `CLAUDE.local.md` and never touches `CLAUDE.md`, so that a repo that already references Praxion is left exactly as the team wrote it.
- **REQ-31** — When onboarding writes Praxion `CLAUDE.md` blocks, and the project has no `CLAUDE.md`, the system shadows `CLAUDE.md` itself by default and writes the blocks there, unless `--share CLAUDE.md` was given, in which case it creates a committed `CLAUDE.md`, so that the operator gets a full private project prompt without introducing a file the team must adopt.
- **REQ-32** — When managed-project detection evaluates the `partially-managed` predicate, the system consults `CLAUDE.local.md` in addition to `CLAUDE.md`, so that a sidecar-placed project is not misclassified as unmanaged.
- **REQ-33** — When the operator selects the CI capability under sidecar placement, the system refuses it with a one-line reason, so that a GitHub-visible workflow surface is never installed into a repo the operator is keeping Praxion-agnostic.
- **REQ-34** — When the operator selects the AaC capability under sidecar placement, the system offers it shadowed and installs the Block D gate into the local hook chain only, so that architecture-as-code works without committing fitness surfaces.
- **REQ-35** — When onboarding stages files under sidecar placement, the system stages project-side files in the project repository and sidecar-side files in the sidecar repository, and never runs `git add` on a path beyond a shadow symlink, so that Phase 9's staging contract holds across two repositories.
- **REQ-36** — When the operator promotes a sidecar, the system moves `.ai-state/` into the project repository preserving its history, removes the shadow links and exclude entries it owns, and leaves a valid in-repo-placement project, so that a decision to go public is mechanical and lossless.
- **REQ-37** — When the operator runs sidecar status or doctor, the system reports placement, identity, sidecar path, per-shadow slot state, hook-chain state, and remote policy, and doctor mutates nothing, so that every legal and illegal state is observable before it is acted on.
- **REQ-38** *(new — `ARCH_WT_RULING.md`; revised 2026-09-02 by § 13 — convergence, not ordering)* — When any channel observes that a worktree's project branch has been merged — the project `post-merge` finalize chain (before draft promotion), the SessionStart heal, or `/merge-worktree` explicitly — the system merges that worktree's sidecar branch into the current checkout's sidecar branch, under the target mount's lock, running `reconcile_ai_state.py` against the mount and using the sidecar's own merge drivers; a branch is merged **only on positive evidence** that its recorded project branch is merged (ancestor, or the squashed-branch patch-id test), and a conflict in an automatic run is **aborted** and reported rather than left mid-merge, so that state written inside a worktree reaches the base branch regardless of which path the project merge took, without depending on an operator or a command remembering to run merge-back first.
- **REQ-39** *(new — `ARCH_WT_RULING.md`)* — When a project worktree is removed, the system removes and prunes its state mount first, refuses removal while that mount is dirty or its branch unmerged, and reports orphaned mounts and unmerged `wt/*` branches from `doctor`, so that the mount lifecycle cannot silently accumulate abandoned state.
- **REQ-40** *(new — `ARCH_WT_RULING.md` § 13)* — When a state branch is unmerged and not eligible — its project branch is not merged, was deleted, has no recorded mapping, or its recorded ref no longer resolves — the system leaves the branch, its commits and its mapping untouched by every automatic channel and deletes a branch only when it is an ancestor of the base branch, so that absent evidence is never read as a merge and abandoned-looking work is never destroyed on a guess; dropping unmerged state requires the explicit two-step path (remove the mount, then `praxion-sidecar merge-back --from <branch> --drop --yes`), refused without `--yes`.
- **REQ-41** *(new — `ARCH_WT_RULING.md` § 13)* — When the operator runs `praxion-sidecar doctor`, the system reports four read-only state and mount rows with stable ids and the exact fix for each — `state-unmerged` (WARN, naming which of the four ineligibility reasons applies), `state-eligible` (WARN), `mount-orphaned` (WARN) and `mount-conflict` (FAIL) — and mutates nothing, so that every convergence state is observable and actionable before it is acted on.

## Acceptance Criteria

### P0 — Hook chaining (independently mergeable)

- [ ] **P0-1** In a repo with `core.hooksPath` set to a foreign directory (husky-style), after onboarding/upgrade a `git commit` runs **both** the team's pre-commit gate and Praxion's id-citation gate, and a `git merge` runs the team's post-merge hook and Praxion's finalize chain.
- [ ] **P0-2** In a repo whose `.git/hooks/pre-commit` is occupied by a non-Praxion hook (pre-commit framework), after onboarding/upgrade the original hook still runs on every commit — it is not displaced and left inert.
- [ ] **P0-3** A delegate (team) pre-commit hook exiting non-zero aborts the commit with that exit code; Praxion's own gates do not run and do not mask the failure.
- [ ] **P0-4** A delegate `post-*` hook exiting non-zero is reported but does not change the chain's exit code, which stays 0.
- [ ] **P0-5** After a package manager re-points `core.hooksPath` (husky `prepare` on `npm install`), the next Claude Code session restores the chain, records the new delegate, and prints one line saying so.
- [ ] **P0-6** Repeated install / upgrade / self-heal runs converge: `core.hooksPath` does not oscillate, and the recorded delegate is never the Praxion wrapper directory.
- [ ] **P0-7** Praxion's own checkout (pre-commit framework in `.git/hooks/pre-commit`, `core.hooksPath` unset, three finalize symlinks) is byte-unchanged by every P0 code path.
- [ ] **P0-8** A project with `core.hooksPath` unset and empty hook slots still receives today's plain symlinks — zero diff versus current behavior.
- [ ] **P0-9** `install_git_hooks.py --status` reports the observed chain state and names any slot where Praxion's hooks cannot fire; `--uninstall` restores the pre-Praxion configuration.
- [ ] **P0-10** No hook step introduced by P0 writes to a git-tracked file.

## Registered Objections

From `ARCH_WT_RULING.md § 10` (first pass) and `§ 14` (second pass), plus `AUDIT_PHILOSOPHY.md § 1.11`'s DS-3 objection:

**§ 10 -- first pass:**
1. **Deviation from the spawn instruction.** Asked to "revise `dec-draft-a3f65ba3` in place"; retired it instead -- under the ruling neither of its two clauses has a subject (`worktree_guard.py` needs no allowance; the dashboard needs no second realpath root). Retirement with a named re-open condition is the honest shape.
2. **Objection to a manifest `mount:` field.** Declined -- a configurable mount name buys nothing an operator wants and costs four readers (CLI, resolver, dashboard TS constant, exclude-block generator) learning a value nobody will change. `.praxion-state` stays a code constant; a collision is a detected, reported state (`ForeignDir`), not a silent overwrite.
3. **This ruling partially walks back `dec-draft-4b33b1df`.** That ADR accepted the loss of branch-scoped isolation as a named cost with a reversal trigger that had not fired. The honest statement: the mechanism was chosen for the write path, and branch-scoped isolation is a *consequence*, not a justification -- arriving with a new cost (merge-back ordering) the shared-live-tree design did not have.
4. **The Stakeholder Review's "unresolved tension" is now resolved in the test lens's favour** -- by a constraint (the harness) neither lens raised, not by foresight.
5. **Scope held** -- no consult disposition re-opened, no CLI verb added/renamed beyond the lifecycle-forced `merge-back`, manifest schema untouched, P0 fragments untouched.

**§ 14 -- second pass (five mechanical objections, all folded into `ARCH_WT_RULING.md § 13`):**
1. **The monotonicity claim is false as written** -- `MergedLive` -> `UnmergedIneligible` is a normal transition (a still-live worktree commits more state post-convergence). Restated as a pure function of current tips; termination rests on finiteness and once-per-run action instead.
2. **"Zero writes at the fixed point" is false unless scoped** -- the squashed-branch test's `commit-tree` probe creates an unreachable loose object in the *project* repository even at the fixed point. Scoped to the sidecar repo + mounts; the probe named as the one exemption.
3. **No state exists for a recorded mapping whose ref no longer resolves** (branch deleted locally and remote-tracking pruned) -- would raise inside a `post-merge` hook. Folded into `UnmergedIneligible` with a named doctor reason; non-raising made an explicit predicate obligation.
4. **`--drop --yes` cannot delete a branch still checked out in its mount** -- as specified, it would fail *after* the operator already confirmed a destructive action. Made two-step: remove the mount first, precondition refused up front and named.
5. **`mount-conflict` FAIL must not claim a rule was violated** -- an explicit `merge-back --from` is *permitted* to leave markers mid-resolution; a read-only `doctor` can't distinguish that from an abandoned mount. FAIL kept (genuinely blocks commits) but the reason string states the fact, not an accusation.

**`AUDIT_PHILOSOPHY.md § 1.11` -- DS-3 objection (ManifestView/MinimalView):** `SYSTEMS_PLAN.md § DS-3` claims "no full parse on the hot path" is a property of the type, because a widening to `FullView` is "a separate call." `ManifestView`/`MinimalView` were never built -- zero consumer needs the widening yet, and the shipped `SidecarIdentity` dataclass already carries only the three identity fields, so the omission itself is judged correct (Incremental Evolution). But the *design document's claim* is now false: with no `ManifestView` in the type system, nothing stops a future consumer from calling `_sidecar_manifest.load_manifest()` on a hook path -- "no full parse on the hot path" is back to being a **convention**, not a type-enforced invariant, and should be corrected in `DESIGN.md`/`docs/architecture.md` rather than left standing.
