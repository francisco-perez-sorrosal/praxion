# Contributing to Praxion

Praxion is a structured layer of reusable expertise — skills, agents, commands, rules, and MCP servers — that operationalizes spec-driven development and context engineering for AI-assisted work.

Contributions follow the conventions documented below. Read the full contributor guide in [`README_DEV.md`](README_DEV.md) for context on project structure and how components work together.

## Getting Set Up

### Prerequisites

- **Python ≥3.11** — required for the core suite (`tomllib` stdlib)
- **Python ≥3.13** — required for `eval/` and `task-chronograph-mcp/`
- **`uv`** — [install via pip](https://docs.astral.sh/uv/getting-started/) or your package manager

### Installation

```bash
# Clone the repository
git clone https://github.com/francisco-perez-sorrosal/Praxion.git
cd Praxion

# Run the installer
bash install.sh

# Verify installation
bash install.sh --check
```

### Activate Pre-Commit Hooks

The installer runs `pre-commit install` automatically. Hooks run on every commit and enforce:

- File hygiene (trailing whitespace, large files, merge conflicts)
- Secret scanning via gitleaks
- Python code formatting and linting via ruff
- Shipped-artifact isolation (no hardcoded `.ai-state/` references in distributed files)
- Canonical-block sync (mirrors content into managed projects)
- Architecture-as-Code golden rules
- Rules manifest coherence

If hooks were skipped, activate them manually:

```bash
pre-commit install
```

## Running Checks Locally

Run these checks before opening a pull request. Pair each check with what it verifies:

| Command | Verifies |
|---------|----------|
| `python3 -m pytest tests/ -q` | Praxion's test suite (core logic) |
| `cd eval && uv run pytest -q` | Eval framework tests (quality measurement) |
| `python3 -m pytest scripts/test_finalize_adrs.py -q` | ADR finalize logic (merge-time promotion) |
| `python3 scripts/sync_canonical_blocks.py --check` | Content shipped to managed projects stays in sync |
| `cd dashboard_app && ./node_modules/.bin/vitest run` | Dashboard package tests |
| `cd dashboard_app && ./node_modules/.bin/next build` | Dashboard production build |

The pre-commit hooks run a subset of these automatically (ruff, gitleaks, isolation checks). The full suite above is what CI verifies.

## Commit Conventions

Commits follow a clear, structured format. See [`rules/swe/vcs/git-conventions.md`](rules/swe/vcs/git-conventions.md) for the full specification.

### Message Format

```
<type>: <subject>

<body>
```

**Subject line:**
- Use imperative mood ("Add" not "Added"; "Fix" not "Fixed")
- Keep under 50 characters
- No period at the end
- Be specific — "Fix null check in auth handler" not "Fix bug"

**Type prefix** (recommended):
- `feat:` — new feature
- `fix:` — bug fix
- `refactor:` — code restructuring without behavior change
- `docs:` — documentation only
- `test:` — adding or updating tests
- `chore:` — maintenance, dependencies, config

**Body** (when context is needed):
- Separate from subject with a blank line
- Wrap at 72 characters
- Explain *what* and *why*, not *how*
- Reference related issues if applicable
- **Never include AI authorship lines** (`Co-Authored-By`, `Generated by`, etc.) — the human owns the commit

### Staging Discipline

- Stage specific files by name — avoid `git add -A` or `git add .`
- Review `git diff --staged` before every commit
- Verify the staged diff matches intent

### What Not to Commit

- Secrets, credentials, API keys, or tokens
- Generated files, build artifacts, or large binaries
- Debug print statements or commented-out code
- Files listed in `.gitignore` (including `.env` with sensitive data)

## Pull Requests

All PRs follow the workflow and safety conventions in [`rules/swe/vcs/pr-conventions.md`](rules/swe/vcs/pr-conventions.md).

**Before opening a PR that touches `.ai-state/`:**

- Run `python scripts/finalize_adrs.py --dry-run` locally and confirm any draft ADRs promote cleanly
- Run the full project test suite (at least `pytest scripts/ -q`)
- Include an explicit note in the PR description: "Touches `.ai-state/`" and list the affected subpaths

**Merge policy:**

- Default: **fast-forward only** (`git merge --ff-only`) — preserves linear history
- **Do not squash-merge PRs that touch `.ai-state/`** — squash erases concurrent state accumulated on main while the branch was alive
- Rebase-and-merge is acceptable if reconciliation scripts are run locally first

**Branch naming:**

- Conventional prefixes: `feat/<slug>`, `fix/<slug>`, `refactor/<slug>`, `docs/<slug>`
- Author-prefixed in multi-user contexts: `<user>/<topic>`
- Kebab-case only

## Crafting Components

When adding or modifying any component type, load the matching skill first to verify spec compliance:

- Adding/modifying a **skill** — load `skill-crafting`
- Adding/modifying a **command** — load `command-crafting`
- Adding/modifying an **agent** — load `agent-crafting`
- Adding/modifying a **rule** — load `rule-crafting`
- Adding/modifying a **hook** — load `hook-crafting`

Each skill has a validator that checks structure, naming, and consistency.
