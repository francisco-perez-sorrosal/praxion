# Known Claude Code Limitations

Claude Code limitations Praxion has hit, with workarounds, tracked here so they can be revisited when Claude Code releases fixes. Each entry is the working summary; full diagnostic detail lives in the linked issue and the `td-NNN` tech-debt-ledger row. Pointed to from the root `CLAUDE.md`.

- **`isolation: "worktree"` on the Agent tool nests worktrees** when the session is already in one (opaque `agent-<hex>` names; fragmented work). Workaround: never pass `isolation: "worktree"` — use `EnterWorktree` + fragment files (the single-worktree policy in `swe-agent-coordination-protocol.md`). Issues [#27881](https://github.com/anthropics/claude-code/issues/27881) (nested creation), [#33045](https://github.com/anthropics/claude-code/issues/33045) (silent ignore for team agents); revisit the policy if both are fixed.
- **Shipped `Explore` subagent crashes during init in many-skill sessions** (Claude Code 2.1.136) — `Agent(subagent_type="Explore", ...)` throws a JS error before the agent starts; not prompt-size dependent; input context is billed with no output (orphaned-tool-start). Workaround: use `praxion:researcher` for substantive code surveys, `find`/`grep` via Bash for narrow lookups; reserve shipped `Explore` for quick single-file lookups only, and expect occasional failures. Tracked as `td-021` (upstream report drafted); same root-cause family as [#38868](https://github.com/anthropics/claude-code/issues/38868).
- **Path-scoped rules (`paths:` frontmatter) reach a new file only after its first write** (re-verified 2026-10-11; first recorded 2026-05-12 as Read-only loading) — Claude Code 2.1.288 made path-scoped rules and nested `CLAUDE.md` load on `Write`/`Edit` too, and 2.1.293 on single-file Bash reads (`cat`, `head`, `sed -n`). The original Read-only gap is closed upstream. What remains: an agent that *creates* a file composes its content inside the first `Write` call, so the rule that call loads arrives after the content is written; later edits see it. The mitigation therefore stays and is now permanent for a different reason: the `implementer`/`doc-engineer`/`test-engineer` prompts read a sibling first, which also covers Cursor (ignores rule globs) and Codex (routes path rules through Praxion's rules bridge). `skills/rule-crafting/SKILL.md` § Path-Scoped Rules: Loading Trigger carries the detail. [#16853](https://github.com/anthropics/claude-code/issues/16853) remains relevant: multi-entry YAML-list `paths:` may fail to parse, while inline arrays (`paths: ["**/*.py", ...]`) and single-entry brace expansion work; `scripts/check_paths_syntax.py` flags at-risk rule files. Windows variant [#21858](https://github.com/anthropics/claude-code/issues/21858): keep path-scoped rules under a project-level `.claude/rules/` if global ones don't load. Tracked as `td-033` (resolved).
- **Subagent `Write` to `.ai-work/<task-slug>/` can be denied by the sandbox** while the main agent's `Write` to the same path succeeds (observed 2026-05-14 with `praxion:systems-architect` writing `SYSTEMS_PLAN.md`). The architect agent has `Write` in its tools whitelist and the target resolves inside the session worktree (so native worktree isolation allows it); the denial appears to be Claude Code's per-tool permission prompt that the main agent had already auto-allowed for this session but the subagent cannot answer interactively. Workaround: when a subagent reports a Write denial for `.ai-work/`, the main agent should place the file from the subagent's returned content — the same pipeline contract is honored, just routed through the orchestrator. Distinct from `td-034` (subagent writes resolve to the wrong tree); same root-cause family in that subagent settings/permission inheritance differs from the orchestrator session. Tracked as `td-035`.
- **`claude agents` is silently refused from inside any Claude Code session** (observed 2026-05-15 during Phase 2 dispatch-reworks pipeline) — the `claude agents` subcommand (the agent-view TUI for monitoring `--bg` sessions) returns `'claude agents' is not available in this environment.` exit 1 when invoked from any child process of `claude`, including the Bash tool inside subagents. The gate is parent-process-based: works from a fresh terminal pane with no `claude` ancestor; fails from inside any Claude session. Workaround: when dispatching `--bg` sessions and wanting to monitor them via agent-view, open a fresh Cursor terminal pane (no `claude` running there) and run `claude agents` from it. Praxion's `scripts/dispatch-reworks` surfaces this instruction in its post-dispatch output. Filed as [#59340](https://github.com/anthropics/claude-code/issues/59340) requesting a more informative error string (the behavior itself is reasonable nested-session defense; the silent generic error cost ~30 min of diagnostic time ruling out env, daemon-state, auth-mode, subscription tier, and binary version before identifying the actual gate). No `td-NNN` row — resolution is upstream-side only.
- **Plugin-distributed subagents silently ignore the `hooks`, `mcpServers`, and `permissionMode` frontmatter fields** (vendor-documented at [code.claude.com/docs/en/sub-agents](https://code.claude.com/docs/en/sub-agents), verified 2026-07-30) — all 17 Praxion agents ship exclusively via `.claude-plugin/plugin.json`, so every such declaration was inert. The documented escape hatch (copy the agent to `.claude/agents/`) is **asymmetric**: the same page states a parent session in `acceptEdits`/`bypassPermissions` takes precedence over any subagent `permissionMode` and cannot be overridden — including for project-level agents — so the hatch can only ever grant more permissiveness, never restore restriction. Workaround: the fields were stripped fleet-wide; agent-level constraint comes from `tools`/`disallowedTools` (honoured) and observability from plugin-level `hooks/hooks.json` (unconditional for every subagent). `tests/test_agent_frontmatter_plugin_compat.py` guards against re-introduction. Tracked as `td-072`.
- **Harness worktree isolation refuses a Bash call by its command text** (observed through Claude Code 2.1.310, 2026-09-24 to 2026-10-27; Praxion's own worktree guard was retired and the harness refuses the same shapes). The message starts "This session is isolated in the worktree" and the refusal is blind text matching, so a compound command runs none of its parts. Refused shapes: a `HOME=...` override, alone or behind `env`; the word `eval` anywhere, even in a directory name; `python3 -` heredocs and `python3 -c` whose text names `git`, or whose program or script path is a shell variable; `git -C <path>`, `git commit -F - <<EOF`, and git inside a pipeline, `$(...)` or `for` loop; a shell variable where a file or option may stand (`sed -n ... "$F"`); the bare word `complete`, which reads as the shell builtin (`step_loop.py record ... --marker complete`); `awk` programs; a loop that runs each line with `sh -c`. Workaround: use plain relative commands from the worktree root, or write the command to a script file in the scratchpad with every argument baked in and run `bash <path>` (the refusal does not read script contents); pass a marker word through a JSON file the script reads. No upstream issue and no ledger row exists for this entry.
- **Write/Edit refuse a file symlink as the target, and worktree isolation is a launch property** (verified 2026-09-02 and 2026-09-03, Claude Code 2.1.258). Beyond the escaping-symlink refusal already recorded in `skills/software-planning/references/coordination-details.md`: Write and Edit also refuse a symlink to a file even when it stays inside the worktree ("it is a symbolic link. Write to the link's target path instead"), while a directory symlink in the path is fine; Claude Code still loads a symlinked `CLAUDE.local.md` and `.claude/settings.local.json`, so a file shadow works for loading but edits must target the real path. Isolation holds only for a session launched into the worktree (`claude -p --worktree <name>`, `EnterWorktree`, resume into a worktree): a bare `claude -p` whose cwd is a linked worktree is not isolated, so a probe of the harness's behaviour uses `--worktree` and carries a positive control (a write into the main checkout must be refused). `permissions.additionalDirectories` did not lift the refusal (settings hot-reload unconfirmed). No upstream issue and no ledger row exists for this entry.
- **`/deep-research` can report "all claims refuted" when every verification vote was rate-limited** (last seen 2026-06): the survive rule scores an abstention (API error, "Rate limited", logged `0-0 (3 abstain)`) the same as a refutation. Read the run's output `logs`; on a rate-limit cascade disregard the verdict, keep the primary-sourced claims from `result.refuted[]` and re-verify the load-bearing ones yourself. No upstream issue and no ledger row exists for this entry.
- **Edit tool quirks, not re-probed since first seen** (2026-05-13 and 2026-10-05). Deleting a whole line: match `<line>\n` (the line with its own trailing newline) and replace with an empty string; matching `\n<line>` consumes the previous line's terminator and fuses its neighbours (table rows fused into one line). A `new_string` ending in a space or tab loses it while `old_string` keeps its own, so the replacement fuses the next token and the tool still reports success: extend both strings to the next non-blank character, and `grep -n` or run the affected tests after any edit whose boundary is whitespace. No upstream issue and no ledger row exists for this entry.
