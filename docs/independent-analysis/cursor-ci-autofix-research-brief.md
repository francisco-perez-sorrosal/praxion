# Research Brief — Autonomous CI/PR Failure Remediation via the Cursor Agent (installable across Praxion + managed projects)

## 1. Mission

Produce an **exhaustive, decision-grade research report** on how to build an **installable mechanism** that lets the **Cursor agent autonomously diagnose and remediate failing GitHub Actions workflows and pull-request checks** — including but not limited to Dependabot PRs — across (a) Praxion's own GitHub repo and (b) every Praxion-managed project, with production-grade guardrails, security, cost controls, and human-in-the-loop (HITL) gates.

**Hard requirement — a per-project installable mechanism.** The end state is NOT a centralized bot/service that reaches into many repos. It is a **self-contained mechanism each project installs into its OWN GitHub repository** — every Praxion-managed repo (and Praxion itself) carries its own copy of the workflow(s) + per-project config + secrets, owns it, version-pins it, and upgrades it independently. `/onboard-project` scaffolds it using the same canonical-asset + onboarding-install dual-source pattern Praxion already uses for `.pre-commit-config.yaml`, `dependabot.yml.tmpl`, etc.; Praxion dogfoods its own copy first. When a workflow run or PR check fails in *that* repo, the repo's own installed automation dispatches the agent (Cursor first, Claude on failover — §I), reads the failure context, applies a fix, pushes it to the correct branch (or opens a fix PR), and closes the loop — gated by that repo's policy.

The deliverable must let a `systems-architect` make an architecture decision (ADR) and an `implementation-planner` produce a build plan **without further research**.

**Leading hypothesis to evaluate — design it concretely if it survives scrutiny (do not assume it; test it).** A **Cursor-first, Claude-as-backup** tiered/failover design: route every GitHub *remote* remediation task (PR fixes, failing-workflow fixes, Dependabot fixes) to the **Cursor agent first** — to spend the user's *prepaid* Cursor credits — and **fail over to `anthropics/claude-code-action`** (which Praxion already runs in CI) only when Cursor is unavailable: credits exhausted, quota/rate-limit hit, API error, or timeout. The elegant framing: **Cursor-credit exhaustion is a NORMAL termination that routes to the backup provider — not a failure** — directly mirroring Praxion's gpu-budget / agentic budget-gate discipline (declare → enforce → exhaustion is expected). The research must (a) determine whether this failover model genuinely beats single-provider, and (b) if so, specify its routing, credit-detection, agent-agnostic task contract, economics, and resilience in implementable detail (see §I). It must steelman the single-provider rejection equally hard — a two-provider stack is real operational cost.

## 2. Concrete grounding — the real failure modes this must handle

These are actual failures resolved manually in a prior session; treat them as the **acceptance test cases** for any proposed architecture. A credible design must explain how the automation would have caught and fixed each:

1. **Dependabot's restricted-token problem.** Dependabot PRs run GitHub Actions with a read-only token and **no access to repository secrets**. A workflow that calls an LLM action (e.g. `anthropics/claude-code-action`) on `pull_request` therefore cannot authenticate — it fails, and downstream `if: always()` steps cascade (e.g. an `upload-artifact` with an empty `path:` → "Input required and not supplied: path"). **Any agent automation that needs secrets must be triggered in a context that HAS them** (the `workflow_run`/`pull_request_target`/default-branch pattern) — research the exact, secure mechanism.
2. **Bot-actor guards.** Actions like `claude-code-action` refuse to run for non-human actors (`dependabot[bot]`) unless explicitly allow-listed. The automation must decide *which* bot/PR events it should act on.
3. **"Re-run" ≠ "rebase."** For same-repo `pull_request` events, GitHub runs the workflow file **from the PR head branch**, and a failed PR branched from old `main` keeps the old (broken) workflows + old base content. A plain CI re-run replays the same broken commit; only a **rebase onto fixed main** picks up fixes. The automation's loop logic must understand this.
4. **Per-dependency branch sprawl.** Dependabot opens one PR/branch per dependency by default (14 at once on a drifted repo); `groups:` collapses them. A general "fix failing PRs" automation must not itself create sprawl.
5. **Pre-existing repo breakage surfaced by PRs.** Some failures (e.g. broken cross-reference links failing `validate_references --all`) are pre-existing and fail *every* PR, not caused by the dependency bump. The agent must distinguish "this PR broke X" from "X was already broken on main."
6. **Stale local/remote ref hygiene + merge strategy.** After fixes, branches must be cleaned and PRs merged with the project's policy (Praxion: linear history / rebase-merge; never squash `.ai-state/`-touching PRs).

## 3. Research questions (exhaustive)

### A. Cursor's GitHub-automation primitives (verify against current 2026 Cursor docs)
- A1. Enumerate every Cursor surface that can run autonomously against a GitHub repo: **Background Agents** (cloud agents), **Bugbot** (PR review), the **Cursor CLI / `cursor-agent` headless mode**, any **Cursor Agents API**, and GitHub-comment triggers (`@cursor`/equivalent). For each: what it does, how it's invoked, what permissions it needs, and its maturity.
- A2. Can a Cursor agent be **launched programmatically from a GitHub Actions runner** (headless `cursor-agent` in a workflow step)? What auth (API key/token) does it need, how is it billed, and can it push commits / open PRs from CI?
- A3. Is there a **Cursor API** to start/monitor/collect an agent run asynchronously (launch from a webhook/Action, poll for completion, fetch the diff/PR it produced)? Document endpoints, auth, rate limits, and async semantics.
- A4. How do Cursor's automations **receive failure context** — can they read GitHub Actions logs, job summaries, artifacts, and the PR diff? What's the idiomatic way to feed "workflow run #N failed, here are the logs" to the agent?
- A5. **Credits/billing**: how are automated/headless/background Cursor runs metered against the user's Cursor credits? Per-run, per-token, per-agent-minute? What cost-control levers exist (max turns, model tier, concurrency caps)?

### B. Trigger architecture (the secure-context problem)
- B1. Compare trigger mechanisms for "a workflow/check failed → launch a fixer agent": `on: workflow_run (types: [completed], conclusion: failure)`, `check_suite`/`check_run`, `pull_request`/`pull_request_target`, scheduled sweeps, and external webhooks → a dispatcher. Which run with **secret access** and which don't, and what are the **security implications** of each (esp. `pull_request_target` + untrusted PR code = the classic privilege-escalation footgun)?
- B2. Specifically solve the **Dependabot-secrets problem** (§2.1): the canonical safe pattern to give a fixer agent secret access while acting on a Dependabot/fork PR. Document `workflow_run` artifact-passing, `pull_request_target` with explicit checkout pinning, and GitHub's "Dependabot secrets" feature — with the security caveats of each.
- B3. How to **avoid infinite loops** (agent pushes a fix → CI runs → fails differently → agent runs again …): concurrency groups, attempt counters, commit-author/actor guards, max-iteration budgets.

### C. The remediation loop (mechanics)
- C1. End-to-end flow: detect failure → gather context (logs, diff, artifacts, failing job/step) → classify failure → generate fix → apply (commit to PR branch vs open a *separate* fix PR vs comment a suggested patch) → re-trigger CI → verify green → report. Document the idiomatic implementation for a Cursor-based version of each step.
- C2. **Failure-type taxonomy + auto-fix safety tiers.** Classify common CI failures (lint/format, type errors, broken doc refs, simple dependency bumps, breaking-API dep upgrades requiring code changes, flaky tests, real logic bugs, security findings, infra/runner failures). For each: is it **safe to auto-commit**, **propose-for-review only**, or **surface-and-stop**? Cite evidence/industry practice for where the auto-fix line should sit.
- C3. Dependabot-specific remediation: rebasing, lockfile conflict resolution, and **adapting code to a breaking dependency upgrade** (the highest-value, highest-risk case). How well can a Cursor agent do this, and what guardrails make it safe?

### D. Comparative analysis (Cursor is primary, but be rigorous)
- D1. Build a **decision matrix** comparing: **Cursor Background Agents / cursor-agent**, **Anthropic `claude-code-action`** (which Praxion ALREADY uses in `claude-code-review.yml` + `context-security-review.yml` — so extending it is the lowest-friction baseline), the **Cursor-first + Claude-backup failover model** (the leading hypothesis — §I), **GitHub Copilot coding agent** (assign-to-Copilot), **Devin / Sweep / others**, and **a self-hosted headless-agent-in-Actions** approach. Axes: cost vs the user's prepaid Cursor credits, security model, control/observability, GitHub-native integration, **per-project installability + version-pinned upgradability across many repos** (a hard requirement — see §F), provider-redundancy/resilience, autonomy ceiling, and fit with Praxion's existing claude-code-action investment.
- D2. **The coexistence question, resolved by the failover hypothesis.** Praxion already runs `claude-code-action` in CI, and the user holds prepaid Cursor credits — so the honest question is not "is Cursor good?" but "is a Cursor fixer *additive*, *redundant*, a *migration*, or a *tiered failover partner*?" The leading answer to design and stress-test is the **Cursor-first + Claude-backup** tiered model (§I): it makes the dual stack *intentional and economically motivated* (spend credits first, Claude on overflow) rather than accidental, and adds provider redundancy. Steelman both the failover model AND the single-provider alternatives (Cursor-only, Claude-only) equally — the credits must not bias the verdict toward maintaining two stacks if one would do.

### E. Security model (treat as adversarial)
- E1. Token scoping / least privilege: exact GitHub permissions an autonomous fixer needs (contents:write, pull-requests:write, actions:read…), OIDC vs PAT vs GitHub App, and how to minimize blast radius.
- E2. **Prompt-injection surface:** a malicious PR (dependency, description, or diff content) attempting to steer the agent into exfiltrating secrets or pushing malicious code. Map this to the `agent-failure-taxonomy` skill's modes (XPIA, tool abuse, excessive agency) and propose mitigations (the `agent-runtime-guardrails` discipline applied to CI).
- E3. The autonomy boundary: when may the agent push to a branch unattended vs require human approval? Reference Praxion's behavioral-contract + HITL conventions.

### F. Installability across Praxion-managed projects
- F1. Package shape: a **reusable workflow** (`workflow_call`) + a thin per-repo caller, a composite action, or a GitHub App? Which is most installable, version-pinnable, and upgradable across N managed projects (mirror Praxion's `upgrade_project_pins.sh` concern)?
- F2. The `/onboard-project` integration: a new Phase (canonical asset in `claude/project-baseline/` + an onboarding sub-step) that installs the workflow + a per-project policy file (which workflows to auto-fix, safety tier, budget, approval mode) + the secrets-setup instructions. Specify the dual-source contract (Praxion dogfoods its own copy).
- F3. Per-project configuration surface: how a project declares *which* failing workflows it wants auto-fixed, the auto-fix safety tier, the cost budget, and the approval policy.
- F4. **Per-repo ownership vs. centralized GitHub App (the load-bearing installability tension).** The hard requirement is *per-project ownership* — each repo carries and version-pins its own mechanism, not a central service reaching in. Weigh the **per-repo reusable-workflow** approach (truly self-contained, each repo owns + upgrades its copy, mirrors Praxion's existing hook/asset model) against a **central GitHub App** (one install, easier fleet management, but the repo does NOT own it — violates the requirement and centralizes the blast radius). Favor and detail the approach that satisfies per-project ownership; if a GitHub App is unavoidable for some capability (e.g. comment triggers), scope it to the minimum and keep the fix logic in the per-repo workflow.
- F5. **Cross-repo secret distribution.** Per-project install means each repo needs its own Cursor + Claude credentials configured. Document how secrets are provisioned per repo (manual, `gh secret set`, org-level secrets with repo allow-lists, GitHub Environments), the least-privilege scoping, and how `/onboard-project` instructs (never auto-injects) the operator to set them. Address how the **Dependabot restricted-token problem (§2.1)** interacts with per-repo secrets — which trigger context can actually read them.

### G. Cost & budget governance
- G1. A budget-gate model for agent runs, mirroring Praxion's **gpu-budget / agentic budget-gate discipline** (declare a budget → enforce → exhaustion is a normal termination, not a failure). Per-run and per-month credit caps; what happens at exhaustion.
- G2. Cost-per-fix estimates and the break-even vs manual remediation, given the user's Cursor credit balance.

### H. Observability & governance
- H1. How to make agent fixes auditable: where the agent records what it changed and why (a fix-report artifact, a PR comment, an entry in `.ai-state/`), and how this composes with Praxion's `observability` skill.
- H2. Metrics: fix success rate, time-to-green, human-override rate, cost-per-fix, regression rate of auto-fixes.

### I. The Cursor-first + Claude-backup failover architecture (the leading hypothesis — design it concretely if it survives scrutiny)

- I1. **Routing / orchestration.** Design the dispatcher that, on a failing workflow or PR, attempts **Cursor first** and **fails over to `claude-code-action`** on Cursor unavailability. Where does the routing live — a single reusable workflow with two conditional provider steps, a composite action, or an external orchestrator? How does it hand *identical* failure-context to whichever provider runs? Must be **per-project installable** (§F) — the routing ships into each managed repo, not centralized.
- I2. **Agent-agnostic task contract (the key to a maintainable dual stack).** Can the remediation task (failure-context → fix → verify) be defined ONCE in a provider-neutral spec that *both* Cursor and Claude consume — same inputs (failing job, logs, diff, allowed tools, safety tier), same output (a diff / fix-commit / fix-PR) — so the fix loop does not fork into two parallel implementations? Sketch this contract. This single-task-two-executors design is what makes failover sustainable rather than "two stacks to maintain."
- I3. **Credit-exhaustion detection & the failover trigger.** Precisely how is "Cursor is out of credits / unavailable" detected? Compare: (a) **pre-flight** a Cursor billing/usage API check before dispatch; (b) **reactive** — run Cursor, catch a quota/rate-limit/credit/timeout error, fall through to Claude; (c) a **health/turn budget**. Document the actual Cursor API surface for usage/quota and the concrete error signatures. **Model the trigger on Praxion's budget-gate discipline: credit exhaustion is a `budget_exhausted`-style NORMAL termination that routes to the backup, not an error** (`rules/ml/gpu-budget-conventions.md` is the precedent).
- I4. **Economic logic — validate, don't assume.** Test the "spend prepaid credits first, pay Claude only on overflow" rationale: do Cursor credits **expire**? Is the plan per-seat or metered? Model cost-per-fix and total cost under low/medium/high failure volumes; identify the volume/credit-balance regime where failover actually saves money vs. adds complexity for marginal savings.
- I5. **Resilience as a first-class benefit.** Beyond cost, failover buys **provider redundancy** — if Cursor *or* Anthropic has an outage/rate-limit, the other covers remediation. Weigh this separately from credit economics; it may justify failover even at cost parity.
- I6. **Quality parity & provider pinning.** Are Cursor- and Claude-produced fixes comparable for CI/dependency remediation? If quality diverges, should certain **task tiers be pinned to one provider regardless of credits** (e.g. breaking-dependency code changes → the stronger model; trivial lint/format → the cheaper)? How is "which agent produced this fix" labeled for audit?
- I7. **Steelman the single-provider rejection (feeds the ADR reversal trigger).** A two-provider failover is exactly the "two agent stacks to maintain" risk — now adopted intentionally. Argue the **single-provider** counter hard: two integrations, two secret/auth setups, two failure modes, and routing logic is real operational + cognitive debt. Under what failure-volume / credit-balance does **Cursor-only** or **Claude-only** dominate? When is failover over-engineering?
- I8. **Failover granularity.** Per-task (try Cursor for this fix, fall to Claude), per-window (Cursor until a daily/monthly credit cap, then Claude), or per-task-type (route by complexity). Recommend the granularity and justify it.

## 5. Source & rigor discipline

- Verify every Cursor capability claim against **current (2026) official Cursor documentation** — Cursor ships fast; training-data knowledge is likely stale. Use the `external-api-docs` skill / web search; cite primary docs.
- Tag every claim **VERIFIED** (≥2 independent reputable sources or primary docs), **SINGLE-SOURCE**, or **UNVERIFIED/marketing**. Never present a vendor's self-description as a benchmark.
- For GitHub Actions security patterns (`pull_request_target`, `workflow_run`, Dependabot secrets), cite **GitHub's official security hardening docs** + ≥1 independent security analysis.
- Adversarially verify the highest-stakes claims (esp. "Cursor can run headless in CI and push commits with secret access safely") — these are load-bearing for the whole feature; a wrong assumption invalidates the architecture.
- Distinguish what is **available today** from what is **announced/roadmap**.

The report is done when a Praxion `systems-architect` could, reading only it, (a) render the **failover verdict** (Cursor-first + Claude-backup vs single-provider), (b) choose the **per-project installable** package shape, and (c) write the ADR — and an `implementation-planner` could decompose the per-repo scaffolding into steps — with no remaining "we'd need to research X" gaps except those explicitly listed as prototype-only open questions.
