# Research Findings: Code Mode & Tool/Skill-Discovery Landscape (External Lens)

**Lens:** codemode-landscape (external / Hat 2 only — no codebase exploration performed per lens scope; internal Praxion inventory is covered by a sibling lens and intentionally not read here).

## Research Goal

Survey the 2025–2026 state of the art in "code mode" and adjacent tool/skill-discovery techniques so Praxion can evaluate how its agents could reach the best of ~80 skills / ~40 commands / MCP tools without paying full listing cost in every session and subagent spawn, or suffering context-rot-driven selection errors.

## Research Questions

1. What exactly is Cloudflare's Code Mode mechanism, and what evidence backs it?
2. What does Anthropic's "Code execution with MCP" post + advanced tool-use features (Tool Search Tool, Programmatic Tool Calling, Tool Use Examples) actually measure?
3. How do Agent Skills achieve progressive disclosure, and does an open standard (agentskills.io) exist? Does Claude Code have (or plan) a skill-search/retrieval mechanism?
4. What is Claude Code's own deferred-tool-loading (ToolSearch) mechanism and its defaults/thresholds?
5. What does the retrieval/context-rot research literature say, with numbers?
6. What do other vendors/practitioners (Speakeasy, GitHub, OpenAI, Block/goose, Vercel, Smithery, Composio, the "bash not MCP" camp, MCP spec WG) converge on or disagree about?
7. What are the security/operational trade-offs of code mode?
8. Which approaches are usable inside Claude Code *today*, and which need harness features Praxion doesn't control?

## External Findings

### 1. Cloudflare Code Mode

**Primary source — Cloudflare Blog, "Code Mode: the better way to use MCP,"** published **2025-09-26**. https://blog.cloudflare.com/code-mode/ (vendor-marketing, but describes a real shipped mechanism — Tier 2, verify-version)

- Mechanism: MCP tool schemas are converted into a **TypeScript API** (with JSDoc) instead of exposed as callable "tools" in the traditional tool-use sense. The model **writes code** that calls this API; the harness executes the code and only the final result flows back into the model's context — intermediate tool outputs (e.g., large JSON blobs, loop iterations) never round-trip through the model.
- Rationale given: (a) models have vastly more real-world TypeScript in pretraining than synthetic tool-call JSON, so code generation is a better-fit task; (b) chaining N dependent tool calls costs N network round-trips to the model in classic tool-use, but O(1) round trips when the whole plan is one code snippet.
- Sandbox: **V8 isolates** via the **Worker Loader API** — a new isolate is spun up per code snippet (millisecond cold start, low memory), executed, then discarded. This is lighter-weight than a container-per-execution model.
- Secrets handling: sandboxed code receives **live object bindings**, not raw API keys/credentials — the binding is pre-authorized server-side, so generated code cannot leak or misuse a credential it never held.
- Evidence: **qualitative only** in this first post — Cloudflare calls results "striking" but publishes no benchmark table. This is a hype-quarantine flag (see below).

**Follow-up — Cloudflare Blog, "Code Mode: give agents an entire API in 1,000 tokens,"** published **2026-02-20** (updated 2026-07-15). https://blog.cloudflare.com/code-mode-mcp/ (vendor-marketing with concrete numbers — Tier 2)

- Introduces the **search() + execute()** two-tool pattern for Cloudflare's own API MCP server (2,500+ endpoints across DNS, Workers, R2, Zero Trust, etc.), exposed through only two tools instead of one tool per endpoint.
  - `search()`: the model writes JS to query a typed OpenAPI representation by product area/path/metadata; the OpenAPI spec itself never enters model context.
  - `execute()`: runs code that performs pagination, conditional logic, and chained calls in a single cycle.
- Quantitative claim: full OpenAPI spec is ~1.17M tokens (or ~2M tokens per a secondary citation); classic per-endpoint MCP tool definitions would cost ~244K tokens even with minimal schemas; the search+execute Code Mode server costs **~1,000 tokens regardless of catalog size** — a claimed **99.9% reduction**.
- Security: runs in a **Dynamic Worker Loader isolate** — no filesystem, no environment variables exposed, outbound network disabled by default (explicit fetch handlers required), and the server layers **OAuth 2.1** token downscoping on top (user grants only the permissions the agent needs).
- Companion docs confirm this is now a **documented Cloudflare Agents pattern**, not a one-off: https://developers.cloudflare.com/agents/model-context-protocol/codemode/ and a dedicated guide "Build a search and execute MCP server," https://developers.cloudflare.com/agents/model-context-protocol/guides/build-codemode-openapi-mcp-server/. Cloudflare's generic `agents/tools/codemode` SDK page (https://developers.cloudflare.com/agents/tools/codemode/) also documents `codemode.search()` / `codemode.describe()` methods for progressive discovery across five surfaces: Durable runtime, AI SDK, TanStack AI, Browser, MCP, and OpenAPI. Explicitly labeled **experimental — "may introduce breaking changes."**

### 2. Anthropic — Code Execution with MCP + Advanced Tool Use

**Primary source — Anthropic Engineering, "Code execution with MCP: Building more efficient agents,"** published **2025-11-04**. https://www.anthropic.com/engineering/code-execution-with-mcp (primary/official — Tier 1)

- Mechanism ("filesystem-of-tools" pattern): MCP servers are presented to the model as a **directory tree of TypeScript files** (`servers/google-drive/…`, `servers/salesforce/…`), each tool a typed module. The agent runs in a **code execution sandbox** and is told "models are great at navigating filesystems" — it lists directories and reads only the tool files it needs, rather than receiving all tool schemas up front.
- Two named strategies for progressive disclosure: (a) plain filesystem exploration (`ls`/`cat`-style navigation), and (b) a `search_tools` function with a detail-level parameter for targeted lookups.
- Sandbox capabilities highlighted: filtering/transforming data before it re-enters model context, loops/conditionals/error handling as ordinary code, automatic **PII tokenization** (e.g., replacing raw emails/phones with `[EMAIL_1]` placeholders before they reach the model), and **state persistence via the filesystem** across steps.
- Explicit caveat from Anthropic itself: *"Running agent-generated code requires a secure execution environment with appropriate sandboxing, resource limits, and monitoring"* — i.e., Anthropic names the security burden rather than hand-waving it.
- **Quantitative claim (headline number):** rebuilding a Google-Drive-to-Salesforce workflow with code execution against the filesystem-of-tools dropped token usage **from 150,000 to 2,000 tokens — a 98.7% reduction**. This is a single worked example, not a benchmark suite — treat as illustrative, not statistically general (hype-quarantine flag).

**Primary source — Anthropic Engineering, "Introducing advanced tool use on the Claude Developer Platform,"** published **2025-11-24**. https://www.anthropic.com/engineering/advanced-tool-use (primary/official — Tier 1)

Three features, each with Anthropic-reported numbers:

- **Tool Search Tool** — tools marked `defer_loading: true` are excluded from the initial context; the model calls a search tool (`tool_search_tool_regex_20251119` or `tool_search_tool_bm25_20251119`) to find and load only what it needs; results expand from a reference into a full definition on load.
  - Numbers: **85% reduction in token usage** while retaining access to the full tool library. On a benchmark with 50+ MCP tools, traditional loading cost ~72K tokens vs ~8.7K tokens with search.
  - **Accuracy went up, not just down in cost**: Opus 4 tool-selection accuracy rose from **49% → 74%**; Opus 4.5 from **79.5% → 88.1%** — i.e., fewer irrelevant tool schemas in context measurably improved selection correctness, not just token spend. This is one of the strongest "less-context-is-better" data points in the corpus.
  - Guidance threshold: recommended when tool definitions exceed ~10K tokens, when accuracy problems are observed, or when 10+ tools / multiple MCP servers are in play.
- **Programmatic Tool Calling** — the model writes Python that orchestrates tool calls inside a sandboxed execution environment; intermediate tool results stay in the sandbox and never enter the model's context window until a final summarized output is returned (structurally identical in spirit to Cloudflare's Code Mode, but Python-based and API-native rather than MCP-external).
  - Numbers: average token usage on complex research tasks dropped from **43,588 → 27,297 tokens (37% reduction)**; knowledge-retrieval accuracy rose **25.6% → 28.5%**; a GIA-style benchmark rose **46.5% → 51.2%**.
  - Guidance threshold: best for large-dataset summarization, workflows with 3+ dependent tool calls, and parallel operations over many items.
- **Tool Use Examples** — an `input_examples` array on a tool definition, giving concrete sample invocations beyond what JSON Schema alone can express.
  - Numbers: internal testing showed accuracy on complex parameter handling rising **72% → 90%**.
  - Guidance threshold: tools with deeply nested structures, many optional parameters with inclusion-order/co-occurrence conventions, or domain-specific API idioms.

Cross-reference: OpenAI shipped a directly analogous `tool_search` / `defer_loading` pair in its Responses API (see § 6), reporting **up to 85% token-cost reduction and up to 47% total prompt-token reduction with GPT-5.4**, and the same 49%→74% accuracy figure appears cited from Anthropic's numbers in secondary OpenAI-ecosystem commentary — treat the cross-vendor citation of identical accuracy figures as **possible convergent measurement or possible citation contamination** (unclear which; flagged in Divergence Map).

### 3. Agent Skills: Progressive Disclosure & the Open Standard

**Primary source — Anthropic Engineering, "Equipping Agents for the Real World with Agent Skills."** (Tier 1, exact date not independently confirmed by fetch — secondary sources place initial Skills launch **October 2025**, spec published as an open standard at **agentskills.io** on **2025-12-18**.)

- Three-tier progressive disclosure, explicit design mental model:
  1. **Discovery** — only `name` + `description` (YAML frontmatter) are ever in context for every installed skill.
  2. **Activation** — the full `SKILL.md` body loads only when the description matches the task.
  3. **Execution** — bundled `references/`, `scripts/`, templates stay on disk, referenced by path, and are read/run only on demand; "context carries an index, not the library."
- Claimed benefit: an agent can have "fifty skills installed" and pay full token cost only for the ones actually activated.

**agentskills.io open standard** (secondary-sourced synthesis, cross-referencing multiple 2026 ecosystem posts — Tier 3, cross-referenced across 3+ sources, moderate confidence):
- Spec requires only two mandatory frontmatter fields: `name`, `description`; everything else (scripts, references, license, allowed-tools, etc.) is optional.
- As of ~June 2026, roughly **40 products** on the agentskills.io showcase claim support, including Claude, OpenAI Codex, GitHub Copilot, VS Code, Cursor, Gemini CLI, Goose, OpenCode, Databricks Genie Code, and Snowflake Cortex Code — i.e., real cross-vendor convergence on the *format*, not just an Anthropic-only artifact.
- Ecosystem quality signal (SkillsBench, cited secondhand — **low confidence, single citation chain, numbers not independently verified against the primary SkillsBench report**): community directories (SkillsMP) index ~1.9M scraped public skills; a SkillsBench audit of 47,150 public skills found an average quality score of 6.2/12, while *curated* skill sets raised agent pass rates by an average of **16.2 percentage points** — i.e., skill quality/curation matters as much as skill selection mechanism. [certainty: low — single secondary aggregator, primary SkillsBench report not directly fetched]

**Claude Code's own skill-listing budget** (GitHub issues + community write-ups — Tier 3/4, cross-referenced across ≥5 independent GitHub issues describing the same symptom, so **higher confidence than a single blog post despite being a low-tier source type**):
- The skill listing budget scales at **~1% of the model's context window** (≈8,000 characters at 200K tokens, using a 4-bytes/token heuristic).
- Each individual skill entry is capped at **1,536 characters** regardless of overall budget; **truncation takes the tail** of the description.
- When the full listing would overflow budget, Claude Code **drops descriptions starting with the least-recently-invoked skills** first — i.e., an LRU-style eviction of *listing text*, not of the skill itself.
- Rule-of-thumb capacity cited: **~15–25 skills** before truncation begins to bite, at the default 1% budget on a 200K-context model — **directly relevant to Praxion's ~80-skill catalog**, which is well past this threshold. [certainty: med — consistent across multiple independent bug reports, but no single authoritative Anthropic doc confirms the exact percentage/cap; treat the specific numbers as reverse-engineered by the community, not officially documented]
- Session-compaction detail: after compaction, Claude Code re-attaches the most recent invocation of each skill (first 5,000 tokens each, 25,000-token combined budget); skills invoked earlier in a long session can be **dropped entirely** post-compaction.

**Claude Code Skill Search — proposed, NOT shipped.** GitHub issue #20143, "[FEATURE] Skill Search/Retrieval Tool" (community feature request, Tier 4 — **not an Anthropic commitment**):
- Proposes a `skill_search(task, context)` interface modeled directly on the shipped Tool Search Tool: return a ranked shortlist of skills with lightweight metadata instead of the full catalog, with pluggable custom registries for organizations with large skill libraries.
- **This is the single most load-bearing "open question" for Praxion**: Anthropic has shipped tool-level deferred loading + search, and skill-level progressive disclosure (description → body → files), but has **not** shipped a skill-level *search/filtering* primitive analogous to `defer_loading` for MCP tools. The gap between "skills load progressively once selected" and "the listing itself doesn't scale past ~20 skills" is exactly Praxion's stated problem, and it is currently **unaddressed by the harness** — see Feasibility Mapping below.
- A parallel, more academic angle: **arXiv:2609.00549, "Skill Following: Evaluating Actual Skill Use in Retrieval-Enabled LLM Agents"** and **arXiv:2607.25032, "Authoring Agent Skills: A Software-Engineering Approach"** — both 2026 papers, not independently fetched in full (title/abstract-level only from search snippets), studying skill-retrieval-enabled agents empirically; one snippet describes a BM25-indexed `search_skills(query)` function returning top-3 full-text skill bodies into context — i.e., academia is already building the exact mechanism Claude Code hasn't shipped. [certainty: low — abstract-level only, not fetched in full]

### 4. Claude Code's Deferred MCP Tool Loading (ToolSearch)

**Primary source — Claude Code Docs, "Scale to many tools with tool search."** https://code.claude.com/docs/en/agent-sdk/tool-search (Tier 1 — official docs)

- Claude Code **defers MCP tool schemas by default**: at session start, only tool *names* and the server's top-level `instructions` field are in the prompt; full input schemas load lazily when Claude searches for a specific tool by name.
- `ENABLE_TOOL_SEARCH` environment variable modes:
  - unset → default (deferred by default)
  - `true` → force deferral through a proxy
  - `false` → load everything upfront
  - `auto` (or `auto:N`) → load definitions upfront while they total under **10%** of the context window (default `N`), deferring past that threshold; `auto:5` sets a custom 5% ceiling.
- Real-world measured example (community, Tier 4 but directly reproducible): deferring 88 tool definitions across MCP servers hid **~40,170 tokens** from the first request that would otherwise have been paid on every turn.
- **Important scope limitation confirmed across multiple sources**: this mechanism applies to **MCP tools only**, not to Skills, not to slash Commands, and (per the open GitHub issue) reportedly does not reliably defer *HTTP/Streamable-HTTP* transport MCP tools in all configurations (issue #40314, unresolved as of the search date — Tier 4, single bug report, not independently verified).

### 7. Security & Operational Trade-offs of Code Mode

Cross-referenced across multiple sources (Tier 3, general agentic-code-execution security literature, not code-mode-specific in every case — see Divergence Map for the scope caveat):

- **Sandboxing is necessary but not sufficient.** Every code-mode vendor (Cloudflare, Anthropic, Vercel) explicitly runs generated code in an isolated environment (V8 isolate / Worker Loader for Cloudflare; unspecified "sandboxed execution environment" for Anthropic's Programmatic Tool Calling; a JS/TS sandbox for Vercel). None claims sandboxing alone eliminates risk — Anthropic's own post names "sandboxing, resource limits, and monitoring" as a compound requirement, not a single control.
- **Prompt injection is the dominant threat model, not code-mode-specific but sharpened by it.** If a tool result (fetched web page, file content, API response) contains an injected instruction, and the model is now *writing code* rather than making a discrete, auditable tool call, the blast radius of a successful injection is larger — the model could write code that chains multiple side-effecting operations in one shot before any human or guardrail sees the intermediate steps. General literature (arXiv:2506.08837, "Design Patterns for Securing LLM Agents against Prompt Injections") and a Microsoft Security Blog post (2026-05-07, "When prompts become shells: RCE vulnerabilities in AI agent frameworks") document concrete RCE and SSRF chains in agent frameworks broadly — none reviewed here demonstrate an exploit specific to Cloudflare's or Anthropic's code-mode implementations by name; treat as a **class-level risk**, not a confirmed vulnerability in the named products. [certainty: med — the general risk class is well-evidenced, but no source found demonstrates a live exploit against Cloudflare Code Mode or Anthropic's Programmatic Tool Calling specifically]
- **Bindings-over-credentials (Cloudflare's approach) is a genuinely different security posture** than "give the sandbox an API key" — it moves the trust boundary to the binding grant (done outside model-controlled code) rather than to code review of what the model wrote. This is a real mitigation, not just marketing, though it is Cloudflare-Workers-specific (Worker Loader bindings) and not portable to an arbitrary agent runtime without an equivalent primitive.
- **Determinism/debuggability trade-off, explicitly named by skeptics (Ronacher) but implicitly conceded by proponents.** A discrete tool call is a single, loggable, replayable event with a fixed schema. A code-mode "plan" is an arbitrary program — replaying it deterministically requires capturing the exact code the model wrote *and* the exact intermediate tool responses it saw, which is a heavier debugging/observability burden than tool-call transcripts. None of the vendor sources reviewed here publish a debugging/observability story as detailed as their token-savings story — this is a **gap in the evidence base**, not a resolved trade-off.
- **Protocol instability (Ronacher's core point) is orthogonal to but compounds the security story**: if an MCP server's tool descriptions change without warning, generated code written against yesterday's schema can fail or misbehave today — a reliability failure mode distinct from, but adjacent to, a security failure mode.

|---|---|---|---|---|
| **A. Static full listing** | Every tool/skill description always in context | Default MCP `tools/list`; Praxion's current skill listing | N/A (baseline) | N/A — this is the thing every other approach measures itself against |
| **B. Deferred/searchable listing** | Names only up front; full schema loads on model-initiated search | Anthropic Tool Search Tool (`defer_loading`), OpenAI `tool_search`/`defer_loading`, Claude Code's default MCP tool deferral | Per-tool | Strong — Tier 1 vendor docs with matching accuracy *and* cost numbers (49%→74%, 85% token cut) |
| **C. Retrieval-routed (meta-tool / search-describe-execute)** | A small fixed set of "router" tools (search/describe/execute) fronts an arbitrarily large external catalog; catalog itself never enters context | Speakeasy dynamic toolsets, Smithery Toolbox, Composio native tools, GitHub `--dynamic-toolsets` (coarser, per-toolset not per-tool), RAG-MCP (academic) | Per-tool or per-toolset | Strong on cost (96–160x reduction claims), explicit cost admitted on call-count (2–3x more round trips) |
| **D. Code-mode / programmatic execution** | Model writes code against a synthesized API (TypeScript/Python); sandbox executes the whole plan; only final result returns to context | Cloudflare Code Mode, Anthropic Programmatic Tool Calling, Vercel `@ai-sdk/code-mode` | Whole-plan (multi-tool per code snippet) | Strong on cost (98.7–99.9% reduction, three independent vendors converge on the *architecture*), weaker on accuracy evidence (Anthropic's PTC numbers are modest: 37% token cut, 3–5pp accuracy gain — much smaller than Tool Search Tool's accuracy gain) and weak on debuggability/security evidence |

| **F. Meta-tool / registry-as-a-service** | A tiny always-loaded router (2–5 tools) queries an *externally hosted* registry, not a locally-defined tool list | Smithery Toolbox (5 meta-tools), Composio, Cloudflare's own `search()`/`execute()` two-tool MCP server | Whole-catalog behind 2–5 tools | Moderate — vendor-reported numbers, architecture is a specialization of C |
| **G. Skill-level progressive disclosure (non-tool)** | Three-tier disclosure of *documents* rather than callable tools: description → body → bundled files | Anthropic Agent Skills / agentskills.io open standard | Per-skill | Strong on the *shipped* mechanism (description/body/files tiering is real and cross-vendor-adopted); **weak/absent on the listing-scalability problem** — no shipped skill-level analogue to `defer_loading` exists yet (see § 3) |
| **H. Protocol-level non-exhaustive listing** | Amend MCP itself so `tools/list` need not be exhaustive; add a `tools/resolve` primitive for named lookups | MCP Progressive Disclosure WG proposal (not yet ratified) | Per-tool, protocol-standardized | Directionally strong case study (Apify's 70K-tool marketplace) but **not yet shipped** — a roadmap item, not a usable mechanism today |

### Trade-offs Summary

- **Approach B (deferred/searchable, e.g., Tool Search Tool)**: Strengths — shipped, on-by-default, measurably improves *both* cost and accuracy, zero extra infrastructure to build. Weaknesses — **MCP-tool-scoped only**; does nothing for Praxion's Skills/Commands catalog, which is the actual bottleneck named in the research goal.
- **Approach C/F (meta-tool retrieval router)**: Strengths — vendor-agnostic pattern, works for *any* catalog (tools, skills, commands) because it's just "a small fixed interface in front of an external index," buildable today as a custom Praxion MCP server or script-backed skill. Weaknesses — more round trips per task (Speakeasy's admitted 2–3x), requires building and maintaining the retrieval index yourself (embedding/BM25 infra, staleness risk), and Ronacher's stability critique applies with full force if the index itself drifts from what's actually installed.
- **Approach D (code mode)**: Strengths — largest headline cost reduction, converged on independently by 3+ vendors (Cloudflare, Anthropic, Vercel) which is a real signal of architectural soundness, not just marketing. Weaknesses — requires synthesizing a typed API surface (nontrivial engineering for a document-shaped catalog like Skills, more natural for a function-shaped catalog like MCP tools/commands), weakest debuggability/observability story of any approach reviewed, newest attack surface, and the accuracy evidence (Anthropic's own PTC numbers) is notably weaker than approach B's — **code mode's advantage is cost, not correctness**, per the evidence gathered.
- **Approach G (skill progressive disclosure, status quo)**: Strengths — already how Praxion works, zero migration cost, cross-vendor-standardized via agentskills.io. Weaknesses — **the listing tier itself does not scale past ~15–25 skills without truncation**, and no shipped Anthropic mechanism (as of this research) closes that gap — Praxion is already past the ceiling with ~80 skills.
- **Approach H (protocol-level non-exhaustive `tools/list` + `tools/resolve`)**: Strengths — would generalize deferred loading beyond Anthropic's proprietary `defer_loading` field to any MCP-compliant client. Weaknesses — **not ratified**; a roadmap item to watch, not a lever to pull now.

## Continuous Improvement Signals

### Skill-catalog listing has no shipped retrieval/deferral primitive, unlike MCP tools

- **Current**: Praxion exposes ~80 skills via flat name+description listing to every session and every subagent spawn (per the task brief and per this session's own observed behavior — this subagent received `claude-ecosystem` and `external-api-docs` skill content injected directly rather than via a search step). Claude Code's skill-listing budget is community-reverse-engineered at ~1% of context / ~1,536 chars per entry / ~15–25 skills before truncation (§3) — well below Praxion's catalog size.
- **Suggested**: No single shipped replacement exists yet, but two converging patterns are buildable today: (a) a **self-built meta-tool router** (Approach C/F: a small MCP server or router-skill exposing `search_skills()`/`describe_skill()` against an index of all SKILL.md frontmatter, modeled on Speakeasy's/Smithery's pattern and the community's proposed-but-unshipped `skill_search` — GitHub issue anthropics/claude-code#20143); or (b) **wait for the MCP Progressive Disclosure WG's `tools/resolve` primitive** to ratify and see whether Anthropic extends the same non-exhaustive-listing idea to Skills.
- **Why suggested over current**: Every retrieval-based approach surveyed here that has *been measured* shows accuracy improving, not just cost dropping, when the model sees fewer, better-targeted candidates instead of the full catalog (Tool Search Tool: 49%→74% accuracy; BoR paper: fixed-5 vs adaptive: 87.1%→93.1% accuracy with Claude Sonnet 4.6 specifically). Praxion's current flat-listing approach is architecturally the same "static full listing" baseline (Approach A) that every other approach in this survey measures itself against and beats.
- **Costs of switching**: Building and maintaining a retrieval index (even simple BM25 over SKILL.md frontmatter) is new infrastructure with its own staleness risk — Ronacher's core critique (protocol/interface instability defeats retrieval-based approaches) applies here too: if the router's index drifts from the actual installed skill set, it degrades trust in exactly the way he describes for MCP tool descriptions. A router also adds a mandatory extra round-trip (search → then use) to every skill invocation, which for Praxion's Direct/Lightweight tiers (single-file fixes) may not be worth the overhead — the router pattern likely earns its cost only at Standard/Full tier where multiple skills are already in play.
- **Recommended urgency**: **consider-next-cycle** — the underlying research signal (fixed-size flat listings are provably worse than adaptive retrieval, converged across ≥3 independent papers/vendors) is solid, but no single shipped mechanism is unambiguously "just adopt this" for the Skills use case specifically; a spike to prototype a minimal router-skill against Praxion's own SKILL.md corpus would be the appropriate next step, not a full migration.
- **Source(s)**: Anthropic advanced-tool-use post (https://www.anthropic.com/engineering/advanced-tool-use); BoR paper (arXiv:2605.24660); GitHub anthropics/claude-code#20143; MCP progressive-disclosure-wg issue #18 (https://github.com/modelcontextprotocol/progressive-disclosure-wg/issues/18).

## Divergence Map

- **Cloudflare/Anthropic/Vercel (code mode) vs. Speakeasy ("you don't need code mode") vs. Ronacher (skeptical of both) on whether a code-execution sandbox is necessary at all.** Cloudflare/Anthropic/Vercel converge on "the model should write code against a synthesized API" as the highest-leverage fix (Tier 1–2 sources, three independent vendors). Speakeasy explicitly counter-argues, in its own headline, that a plain three-meta-tool (search/describe/execute) pattern over *ordinary* tool-calling achieves comparable-or-better token reduction (96%+ vs. 98.7–99.9%) **without** a sandbox, at the admitted cost of more round trips (Tier 3, single vendor, not independently replicated). Ronacher (Tier 3, independent practitioner) argues both miss the actual bottleneck — protocol/schema **instability**, not verbosity — and that neither fixes agents whose external tool descriptions change out from under them. **No source in this survey adjudicates between these positions with a shared benchmark**; the token-reduction numbers on each side come from different tasks/catalogs and are not head-to-head comparable. [certainty: low — divergent claims, no shared benchmark, resolve only by Praxion running its own comparison if this becomes decision-relevant]
- **Magnitude of code-mode token savings (98.7% Anthropic vs. 99.9% Cloudflare vs. 99.9% Vercel) looks like convergence but may be citation/framing contamination, not independent measurement.** All three numbers come from a *single worked example* per vendor (a specific workflow or a specific large OpenAPI catalog), not a shared benchmark suite. The similarity in magnitude is suggestive of the same architectural pattern producing similar order-of-magnitude effects on the same *class* of problem (huge tool catalog reduced to a compact code-callable API), but should not be read as three independent replications of the same number. [certainty: med — architecturally consistent, but not statistically independent evidence]
- **OpenAI's cited 49%→74% accuracy figure appears identical to Anthropic's Tool Search Tool number** in secondary OpenAI-ecosystem commentary (MindStudio blog). This is either (a) OpenAI's own GPT-5.4 tool-search benchmark independently landing on the same figures as Anthropic's Opus 4 benchmark (unlikely coincidence, different models/benchmarks), or (b) a secondary source conflating/misattributing Anthropic's number to OpenAI's feature. **Not resolved by this research** — flagged as a citation-hygiene risk; do not repeat the 49%→74% figure as an OpenAI-specific result without checking OpenAI's own primary benchmark page directly. [certainty: low — likely secondary-source contamination, unverified]
- **No divergence found** between Anthropic's Agent Skills progressive-disclosure design and the agentskills.io open-standard description — cross-vendor secondary sources describing the ~40-product showcase are consistent with Anthropic's own three-tier design language.
- **No divergence found** on the existence of a tool-catalog-size accuracy penalty — every source in § 5 (Chroma, LongFuncEval, BoR paper, tool-overload synthesis) agrees larger uncurated catalogs degrade accuracy; they disagree only on magnitude and mechanism (attention dilution vs. semantic-distractor confusion vs. protocol verbosity), which is expected variation across different experimental setups rather than a true contradiction.

## Open Questions

1. **Does Anthropic plan to ship a Skill-level analogue of `defer_loading`/Tool Search Tool?** GitHub issue #20143 is a community request, not a confirmed roadmap item — no Anthropic commitment found in this research.
2. **Will the MCP Progressive Disclosure WG's `tools/resolve` proposal actually ratify**, and on what timeline? If it does, it would generalize deferred loading to any MCP client, reducing the need for Praxion to build a bespoke router.
3. **Is there a documented debugging/observability story for any shipped code-mode implementation** (Cloudflare, Anthropic PTC, Vercel)? None of the primary sources fetched here address this in the same depth as their cost numbers — this is a genuine gap, not just an omission from this survey.
4. **Has anyone benchmarked code-mode vs. meta-tool-router vs. deferred-loading head-to-head on the same task/catalog?** No such comparative study was found; all vendor numbers are self-reported on self-chosen tasks.
5. **What is the actual current size and shape of Praxion's skill/command/MCP-tool surface** (exact token cost of the current listing, exact truncation behavior observed in practice)? This external lens deliberately did not investigate the Praxion codebase — that quantification belongs to the internal-lens sibling document.
6. **Does Claude Code's skill-listing LRU-eviction-by-recency interact badly with Praxion's subagent-spawn pattern**, where each subagent starts a fresh session with no prior invocation history to rank skills by recency? If so, every subagent spawn may see the *same* arbitrary truncation rather than an adaptive one — not confirmed here, worth an internal-lens follow-up.
