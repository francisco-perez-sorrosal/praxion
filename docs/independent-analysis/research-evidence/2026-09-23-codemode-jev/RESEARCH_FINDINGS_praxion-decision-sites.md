# Research Findings: Praxion Decision Sites for Jev (System-One Model) Integration

Lens: **praxion-decision-sites** (internal codebase + fit). Collected independently — no cross-reference to sibling lenses.

## Research Goal

Inventory every place in Praxion where a small, typed decision (routing, classification, gate verdict) is currently made by an LLM, a brittle heuristic, or a human — because automation was too costly or the mechanism too coarse — and assess fit for offloading to Jev's three primitives (Choice / Score / Noul).

## Research Questions

1. Where does Praxion make small, bounded, typed decisions today, and by what mechanism (LLM / heuristic / manual)?
2. For each site: shape, input size, frequency, cost/latency, failure mode, Jev fit, integration surface, blast radius.
3. What architectural constraints (runtime, secrets handling, offline expectations, portability, privacy) bound any Jev integration?
4. Where does calibrated confidence enable something new (confidence-gated escalation, ensembles) rather than a like-for-like swap?

## Codebase Findings

### Runtime and architectural constraints

- **Hooks are Python3, stdlib-only, ambient-interpreter.** `hooks/hooks.json` registers every hook as `python3 ${CLAUDE_PLUGIN_ROOT}/hooks/<name>.py`, invoked under whatever `python3` is on `PATH` — no guaranteed venv. `rules/swe/gate-liveness.md`'s `ambient-import` clause (enforced by `scripts/check_gate_liveness.py --check ambient-import`) treats a third-party import in an ambient-invoked script as a liveness violation. **Any Jev SDK call from a hook must go through `urllib.request`/stdlib HTTP, or be gated behind a `try/except ImportError` with a real fallback (not just a swallowed exception, which the same check flags).**
- **PreToolUse hook timeouts are tight.** `hooks/hooks.json`: the `Bash` matcher's commit gates run at 20–30s timeouts; `SessionStart` hooks run 5–35s. A synchronous network round-trip to a third-party inference API inside one of these gates risks the timeout on a slow network, and Claude Code's PreToolUse-hook exit-code semantics (`hooks/commit_gate.sh`) make a hook crash **fail open** (non-blocking, `exit 1` is swallowed unless wrapped `--blocking`) — a Jev outage would silently disable the check rather than hard-block, which is probably the right default but must be a deliberate design choice, not an accident.
- **Third-party API keys already flow through two precedents**, both worth mirroring: (1) `external-api-docs`/context-hub — `CHUB_TELEMETRY=0 CHUB_FEEDBACK=1` env vars, Node.js CLI, graceful fallback to web search when unavailable (`skills/external-api-docs/SKILL.md` § Fallback Hierarchy); (2) `eval/trajectory_eval.py --judge openai/gpt-4o` — a third-party (non-Anthropic) LLM judge already lives in the codebase, gated by `provider, model_name = args.judge.split("/", 1)` and presumably an `OPENAI_API_KEY` env var (not itself present in the file — inherited from the `phoenix.evals` `LLM` wrapper). CI secrets follow the same shape: `.github/workflows/reusable-ci-autofix.yml:266` uses `secrets.CLAUDE_CODE_OAUTH_TOKEN`. **A `JEV_API_KEY` (or similar) env var, absent-means-skip, is the established idiom — not a new pattern.**
- **Graceful degradation has a named idiom already: the "TT idiom" / substrate trigger.** `agents/sentinel.md` skips checks with an INFO note (never WARN/FAIL) when a dependency's substrate is absent (e.g., `scripts/check_gate_liveness.py` absent → skip GL02/GL04/GL05 with an INFO note). Any Jev-backed check should skip-with-INFO, not fail, when the API key/network is unavailable — consistent with existing sentinel and `external-api-docs` conventions.
- **Portability is currently uneven, and precedent exists for Claude-only scope.** `rules/swe/agent-model-routing.md` frontmatter declares `codex: portability: claude_only` — this specific rule (the model-routing tier table) is **not** exported to Codex/Cursor via `install.sh cursor`, even though skills/agents/commands are nominally assistant-agnostic (root `CLAUDE.md`: "Assistant-agnostic shared assets at repo root"). A Jev integration expressed as a Claude Code **hook** is inherently Claude-Code-only (Codex and Cursor have no equivalent hook surface); a Jev integration expressed as a **skill** (agent-invoked, not harness-invoked) is portable in principle.
- **No prior ADR blocks or governs a third-party inference-API dependency for routing/classification.** `grep`-scanning `DECISIONS_INDEX.md` for "third-party model", "external model", "classifier model", "small model", "routing model" returned no hits. The closest precedent is **dec-225** (`.ai-state/decisions/225-remove-in-house-memory-subsystem.md`) — Praxion removed its in-house curated-memory engine specifically "leaving a clean seam for the external `sandbook` memory package." This is precedent *for* delegating a well-scoped subsystem to an external package via a clean seam, not against it — but it is about memory, not inference routing, so it's suggestive rather than directly on point.
- **Privacy**: no code in Praxion currently sends source diffs or file content to a third-party inference API from a **hook** (the eval judge sends trace/span data, which is observability data the user already opted into via Phoenix, not raw source). A Jev integration that sends diff text or plan prose to an external endpoint from a hook is a **new privacy surface** with no existing opt-in gate to model itself on except `CHUB_TELEMETRY`'s env-var opt-out pattern — this should be treated as an open question, not resolved by analogy alone.

### Sites reviewed and excluded (with reason)

- **`check_id_citation_discipline.py`, `check_token_ratchet.py`, `check_shipped_artifact_isolation.py` and siblings** — these are **CODE-kind gates** per `rules/swe/gate-liveness.md`'s own taxonomy: deterministic regex/AST pattern matches over an identifier *shape* (`REQ-NN`, `dec-draft-<hash>`), each proven with a canary test that feeds a known-bad input. They are not "brittle" in the judgment sense the task asked about — they are precise, and Gate Liveness explicitly requires CODE gates to stay deterministic and canary-provable. Replacing them with a probabilistic Jev call would be a regression against the gate-liveness discipline itself (a Jev Noul call cannot be canary-proven the same way, and the whole point of these checks is that the pattern is unambiguous).
- **`worktree_guard` command-text heuristics** — per `docs/claude-code-limitations.md` and this session's own live behavior, these Bash-text refusals were **retired in v0.30.0 (dec-379)**; worktree isolation is now a native harness mechanism, not Praxion code. No live decision site to improve.
- **Tech-debt ledger `dedup_key` derivation** (`scripts/finalize_tech_debt_ledger.py`) — a deterministic string derivation from category+location, not a judgment call. Not a candidate.
- **`resolve_test_scope.py` radius widening** — deterministic path-matching with a deliberate safe-default ("an unmatched path WIDENS the radius"). Already well-designed for uncertainty (fail toward the larger, safer test scope); not a judgment call needing a model.
- **Skill/agent/command selection by the main session** (which skill's `description` matches the current task) — this is the Claude Code harness's own native semantic-routing mechanism (frontmatter `description` matching), not Praxion-owned code. Out of scope for a Praxion-side integration.
- **Praxion's own compaction hooks (`precompact_state.py`, `inject_compaction_orientation.py`)** — worth naming explicitly because the task brief invited comparison to `fast-jev-compaction`. Praxion's compaction hooks do **not** perform per-tool-call keep/truncate/drop decisions today; per `docs/context-economy.md:11-12`, "Praxion sets none of those controls, ships no threshold, and reads no utilisation" — the hooks only **snapshot pipeline state** before compaction and **re-orient** after it. There is no existing brittle heuristic here to replace; a Jev-driven content-selection compaction hook would be a **net-new capability**, not a swap, and would need to be designed from scratch (closer to `fast-jev-compaction`'s own territory than to anything Praxion currently does).

## Candidate Classification: Easy Proofs of Integration → Elaborate

**Tier 1 — Easy, low-risk, high-signal proof points** (small state, bounded Choice, advisory-only blast radius, no codebase lookup needed):
1. `eval/trajectory_eval.py` tool-selection judge (#1) — drop-in replacement for one `create_classifier` call; the harness (Phoenix) already exists, the state (one span) is already small, and the current mechanism is *also* a third-party LLM call, so this is a same-shape swap, not a new integration pattern.
2. `detect_duplication.py` duplicate-confirmation (#9) — a second-pass confidence check behind an existing, already-safe heuristic; worst case is unchanged from today (a missed or spurious WARN).
3. ADR `architectural` category self-check (#5) — a Noul/Choice call the ADR-authoring skill can run against text it already has in hand, surfaced as an advisory nudge before commit, not a gate.

**Tier 2 — Medium effort, needs a confidence-gating design, real value if it lands:**
4. CI-autofix flake-pre-filter (#2) — highest potential cost savings in this inventory (60-turn budget per false-positive fix attempt), but requires defining a conservative confidence floor and a safe "escalate to the full agent" fallback; getting the floor wrong has asymmetric cost (skipping a real fix is worse than an unnecessary full diagnosis).
5. Sentinel Pass-2 semantic checks (#7) — plausible per-check, but sentinel batches artifacts for token-budget reasons today; redesigning the batch boundary around per-artifact Jev calls (with LLM escalation on low confidence) is a real design exercise, not a drop-in.
6. Tier-selection soft-signal scoring (#3) — valuable (highest-frequency classification in the ecosystem) but touches the Intake Clarity Gate's UX; needs care not to make tier selection feel like a black box the user can no longer inspect (the current design explicitly surfaces per-signal reasoning to the user for override).

**Tier 3 — Elaborate, needs architectural groundwork first:**
7. Verifier sub-classification splitting (#6) — the highest blast-radius site (pre-merge gate) and the one needing the most surgery: separating verifier's ~20 PASS/FAIL/WARN sub-checks into "mechanical once evidence is assembled" vs "needs multi-file reasoning" is itself a design task, and any Jev involvement here should launch only as a second opinion surfaced alongside the LLM's own verdict, never a silent override.
8. Researcher spawn-mode routing (#4) and calibration retrospective (#10) — low individual value (infrequent, or already free), worth bundling into a broader "orchestrator decision assist" pattern only if #3 and #7 prove out first.
9. A `fast-jev-compaction`-style compaction hook — explicitly **net-new** for Praxion (no existing heuristic to replace), the largest privacy-surface question (diff/file content leaving the machine from a synchronous hook), and the one site most constrained by the ambient-stdlib-only hook runtime and the tight PreToolUse timeout budget. Recommend this only after the architectural constraints (privacy opt-in gate, offline degradation, Codex/Cursor portability) are resolved at the design stage — likely the systems-architect's call, informed by whatever the product-deep-dive lens reports about Jev's actual latency/offline characteristics.

## Open Questions

- Does Jev support on-device/local inference with sub-millisecond latency? This single fact flips site #8 (`capture_observations.py`) from "weak fit" to a genuinely interesting candidate, since the shape match is excellent and only the cost/latency axis disqualifies it today.
- What is Praxion's actual privacy posture for sending diff/plan text to a third-party inference endpoint from a hook that runs in *every* managed project, not just Praxion's own repo? No existing ADR resolves this; `CHUB_TELEMETRY`'s opt-out-by-env-var pattern is the closest precedent but was designed for documentation retrieval, not code content.
- Should a Jev integration ship as a **skill** (portable, agent-invoked, works across Codex/Cursor in principle) or a **hook** (Claude-Code-only, harness-triggered, matches `fast-jev-compaction`'s own integration pattern)? These have materially different portability and blast-radius profiles and the answer likely differs per site (e.g., the eval judge swap is naturally a script change; a compaction hook is inherently harness-specific).
- For sites #6 (verifier) and #7 (sentinel), what does "escalate to LLM on low Jev confidence" cost in practice — does the ensemble pattern (Jev-first, LLM-fallback) actually save meaningful spend once the confidence floor is tuned conservatively enough to avoid false-negatives on a pre-merge gate?
