# Agentic Transactions Design Review Checklist

Use this checklist to audit a transaction-layer design — an agentic payment flow (Space A) or an agentic trading flow (Space B) — before implementation, when reviewing a `TRANSACTIONS_DESIGN.md` artifact, or when running `/review-transactions` against a provider integration. Back to [SKILL.md](../SKILL.md).

Skip whole sections that do not apply (a payments-only design has no order lifecycle); never skip **Enforcement Locus**, **HITL Gating and Irreversibility**, or **Sandbox and Real-Money Guardrails** — those three apply to every transaction design in both spaces.

## Provider Contract Conformance

- [ ] All six core verbs are accounted for: `resolve_identity`, `create_mandate`, `get_quote`, `authorize`, `execute`, `get_receipt`
- [ ] Any verb the provider cannot serve natively is mapped to an explicit substitute (e.g. an out-of-band account setup standing in for `create_mandate`), not silently dropped
- [ ] `transport_kind` is declared (`mcp-client` or `http-sdk-client`) and the design does not assume a transport the provider lacks
- [ ] Every optional capability the design calls (`get_market_data`, `list_positions`, `list_orders`, `cancel`, `replace`) is gated on its declared capability flag, not assumed present
- [ ] Provider-specific divergence rides in `rail_detail` / `venue_detail`, not in new fields bolted onto the common core
- [ ] The design would accommodate a second provider without changing the core verbs — only a new plugin descriptor and provider reference

## Mandate Model

- [ ] `max_amount` and `currency_or_asset` are both specified — a ceiling without a unit is not a ceiling
- [ ] A `time_window` bounds mandate validity; the design states what happens when an execution is attempted after expiry
- [ ] `constraints` enumerate the non-amount limits (symbol/merchant allowlist, side, order type, counterparty) rather than leaving them implicit
- [ ] `human_present` is set truthfully — an unattended batch job must not claim an interactive human approved the mandate
- [ ] The mandate carries a provider-issued `signature` (or the design states explicitly that the provider issues none and what compensates)
- [ ] Mandate lifecycle is defined: who creates it, when it is re-issued, how it is revoked mid-flight
- [ ] Cumulative spend across multiple executions under one mandate is tracked — a per-call cap that resets each call is not a budget

## Enforcement Locus — Asserted vs. Enforced

- [ ] Each stated guardrail names the **component** that enforces it, not just the rule
- [ ] The spend ceiling is checked in the provider plugin or tool/transport boundary — deterministic code the model cannot reach — before the order or payment leaves the process
- [ ] No guardrail's sole enforcement is text in a system prompt, tool description, or agent instruction
- [ ] The boundary check re-derives the amount from the request being sent, not from a model-supplied field asserting the amount
- [ ] Constraint violations raise `mandate_denied` from the enforcement point rather than relying on the model to decline
- [ ] The design states what an adversarial or confused model attempting to exceed the cap actually hits (rejected call), not what it is instructed not to do
- [ ] Where the provider also enforces a limit server-side, the design says so — and does not treat provider-side enforcement as a substitute for the local check, or vice versa

## HITL Gating and Irreversibility

- [ ] Every operation with an irreversible effect is enumerated, and each one is either behind a human gate or has a written, reasoned exemption
- [ ] `approval_mode` is stated per operation (`autonomous` / `human_gate` / `hybrid`), not once for the whole provider
- [ ] A preview-before-execute step exists: the human sees the concrete quote/order (amount, asset, side, price, fees, warnings) — not a paraphrase generated by the model
- [ ] The gate blocks `execute()`; approving a *plan* is not approving an *execution*
- [ ] The design states whether the provider enforces the gate or whether the agent loop must — and where the provider does not enforce it, the local gate is mandatory
- [ ] The gate is durable across process restart (persisted pending-approval state), not a blocking in-process prompt whose loss silently drops or re-fires the action
- [ ] Rejection path is defined: a denied approval discards the pending execution and does not leave a partially-authorized state
- [ ] Approval is bound to the specific quote/idempotency key it approved — an approval cannot be replayed against a different or re-quoted execution
- [ ] Timeout behavior on an unanswered gate defaults to *not executing* (fail-closed), and expired quotes are re-quoted rather than executed stale
- [ ] Every gate decision is logged with who approved, what was shown, and when

## Idempotency and Retry Safety

- [ ] `idempotency_key` is required on every `authorize` and `execute`
- [ ] The same key is reused on retry (a fresh key per attempt is a duplicate-transaction bug)
- [ ] Key generation and lifetime are specified — where the key is derived from and how long the provider honors it
- [ ] Retry policy is bounded (max attempts, backoff, jitter, outer timeout budget), not an unbounded loop
- [ ] Ambiguous outcomes (timeout, connection drop after send) resolve by querying execution state, not by blindly re-sending

## Settlement Finality (Space A — payments)

- [ ] `finality` is declared per rail (`immediate` / `t+1` / `on-chain` / `async`) and matches what the rail actually does
- [ ] `reversibility` is declared, and the design does not assume a chargeback/refund path on an irreversible rail
- [ ] Async or pending settlement is modeled as a state to poll (`finality_pending` → `get_receipt`), not as a synchronous return value
- [ ] The design says what state the system is in between `execute` and settlement, and what a crash in that window leaves behind
- [ ] Rail selection is justified against the reversibility and finality the use case needs, not chosen by convenience
- [ ] On-chain specifics (chain id, gas/fee policy, confirmation depth treated as final) are stated where an on-chain rail is used
- [ ] Receipts are retained with `signed_proof` and are sufficient to reconstruct what was paid, to whom, under which mandate

## Order Lifecycle (Space B — trading)

- [ ] Order states are modeled end to end: `pending` → `submitted` → `partial` → `filled` / `rejected` / `canceled`
- [ ] Partial fills are first-class — the design does not assume one order yields one fill event
- [ ] `fills_async: true` is honored: the flow does not block on `execute()` for a final quantity or price
- [ ] Position and buying-power state is re-read after fills rather than inferred from what was requested
- [ ] Market-hours handling is specified (regular / extended / closed) including what happens to an order placed while closed
- [ ] Order type is chosen deliberately; where a market order can fill far from the quote, the risk is stated or a limit is used
- [ ] Cancel and replace semantics are defined, including the race where a cancel arrives after a fill
- [ ] Asset-class limits of the provider (e.g. long-equities-only) are stated and the design stays inside them

## Sandbox and Real-Money Guardrails

- [ ] `supports_sandbox` is stated explicitly for the provider — not left unknown
- [ ] Where `supports_sandbox: true`, the design says how sandbox vs. live is selected and how a live credential cannot be picked up by a test run
- [ ] Where `supports_sandbox: false`, the design acknowledges that every test iteration is a real transaction
- [ ] Where `supports_sandbox: false`, a capital-segregated account or budget-capped instrument is mandatory and specified — the deposited amount is the real ceiling
- [ ] Where `supports_sandbox: false`, the HITL gate is mandatory and enforced locally, defaulting to `human_gate` on every execution
- [ ] A local simulation/dry-run path exists for developing the flow shape without transacting, and it is clearly distinguished from a provider sandbox (it proves the code path, not the venue behavior)
- [ ] Credentials for live and test are separated, and no live credential is reachable from the default developer configuration

## Error Grammar

- [ ] Every provider error maps to exactly one code in the closed `TransactionError` set; no ad-hoc codes are introduced
- [ ] `retriable` and `step_up_required` are set for each mapped error, and the retry logic branches on those flags rather than on message text
- [ ] `approval_required` routes to the human gate, not to an automatic retry
- [ ] `quote_expired` re-quotes rather than executing the stale quote
- [ ] `finality_pending` polls `get_receipt` and is not treated as a failure
- [ ] Provider-specific decline/reject detail is carried in `detail` / `rail_detail` / `venue_detail`, not by widening the enum
- [ ] Transport failures (connection loss, reconnect exhaustion) map to `provider_unavailable` with a bounded backoff before being surfaced as terminal
- [ ] Error messages surfaced to the model steer toward a correct next action rather than exposing raw provider internals

## Provider Terms, Access Scope, and Regulatory Posture

- [ ] The design states what the provider's terms permit an autonomous agent to do, and stays inside it
- [ ] The **read** scope granted is documented separately from the **write** scope — a narrow write boundary is not a data-isolation boundary, and the breadth of readable account data is surfaced to the user
- [ ] Where the provider disclaims supervision of agent behavior, the design names the mitigations that bound (not eliminate) the transferred risk
- [ ] Jurisdictional and eligibility limits (geography, account type, asset class) are stated
- [ ] Audit trail is sufficient to reconstruct, per transaction: identity, mandate, quote, approval decision, execution, receipt
- [ ] Credentials are never committed; token lifecycle (refresh, revocation, re-auth on expiry) is defined

## Churn Resilience

- [ ] Volatile provider specifics (auth scopes, rate limits, order-type enums, endpoint URLs, tool schemas) are marked "verify at use time" and not baked into the design as fixed values
- [ ] The design names how the provider's live surface will be introspected or re-fetched before implementation
- [ ] Rate limits are either known or explicitly flagged as unknown with a conservative default

## What This Checklist Does Not Cover

Three things in this domain resist checkbox review and need reviewer judgment — flag them as narrative findings rather than forcing a box:

- **Is the mandate ceiling the *right* number?** Conformance can verify a cap exists and binds; only the user's risk tolerance decides whether the figure is sane.
- **Is autonomy appropriate for this operation at all?** A well-gated design for a flow that should never have been agentic still fails. This is a judgment about the use case, not the mechanism.
- **Is the provider trustworthy for this capital?** Counterparty and custody risk sit outside the design artifact.

## Quick Verdict Guide

| Finding count | Verdict |
|---------------|---------|
| 0 FAIL, 0 WARN | PASS |
| 0 FAIL, 1–3 WARN | PASS WITH FINDINGS |
| 0 FAIL, 4+ WARN | PASS WITH FINDINGS (significant) |
| 1+ FAIL | FAIL |

FAIL items: an irreversible operation with no human gate and no reasoned exemption; a spend cap enforced only in prompt text; `supports_sandbox: false` without both a capital-segregated budget and a locally-enforced HITL gate; missing `idempotency_key` on `authorize`/`execute`; async settlement or partial fills modeled as synchronous; errors outside the closed `TransactionError` grammar; live credentials reachable from a test path.

WARN items: `supports_sandbox` stated but selection mechanism unspecified; unbounded or unspecified retry policy; volatile provider specifics frozen into the design; missing cancel/replace race handling; incomplete audit trail; market-hours behavior unstated.
